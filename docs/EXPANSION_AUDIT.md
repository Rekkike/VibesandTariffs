# Port-Expansion Readiness Audit — findings document

**Audit pass type:** audit-only. No code, no data, no figures, and no spec version/changelog row were changed by this pass. The only artifact is this document. The version guard (`core/scripts/check_spec_version.js`, `BEHAVIOR_PATHS = core/src/, core/data/, core/scripts/, web/src/`) does not read `docs/EXPANSION_AUDIT.md`, so the changelog-row convention does not demand recording the audit itself; the row convention is reported here, not decided.

**Baseline audited:** `main` at `c5d78d9` (v0.2.58), clean tree. Both suites run green at the baseline before any reading: **core 449/449** (`cd core && npm test`), **web 275/275** (`cd web && CI=true npx react-scripts test --watchAll=false`, after `npm install` per workspace per ADR-001, `npm run build` in core, and `node scripts/convert_yaml_to_json.js` to regenerate the gitignored `web/src/data/ports.json` — the only sandbox-side setup; the working tree stayed clean of tracked-file changes). Nothing was rebuilt beyond that: no production build was made or is claimed.

**Question 1 — "is the code optimized enough to handle more data sets?" Honest answer: the data pipeline mostly is, but four load-bearing code sites are not.** The engine, loader, conversion script, and classifier are already per-port-generic (a new YAML file loads, validates, classifies, and reaches the UI with zero code edits; `core/scripts/convert_yaml_to_json.js:14-19` documents the contract and it holds). But `defaultCall` (`core/src/defaults.ts:30-136`), `OPS_COMPONENTS_BY_PORT` (`core/src/engine.ts:1536-1557`), `toComparisonBasis`/the SEK-only comparison basis (`web/src/conversion.ts:63-77`, `core/data/exchange_rates.yaml`), and the per-port input gates in `PortWorkspace` (`web/src/App.tsx:969, 1157, 1257, 1368, 1660`) all require editing an enumeration to add a port, a currency, or an operator list. Three ports at these sites is an accident of history, not a design limit — but five to eight ports will trip all four repeatedly. Details in item A.

**Question 2 — "is the UI workable at more ports?" Honest answer: no, not at eight, and only marginally at five.** The comparison table has no per-column width bound (`web/src/index.css:838-841`: `width: 100%`, no `min-width` per column, no column-count breakpoint); at eight ports the per-GT and converted secondary lines force horizontal scroll of the whole container (`overflow-x: auto` at `index.css:833-835`) — the fit contract (spec v0.2.43) holds only while figures stay narrow. The mobile card stack is linear in ports (one `.comparison-port-card` per selected port, `App.tsx:2943-3012`): eight ports is eight full cards to scroll through, with no subset control in the flow. The port picker is a scrollable MUI `Tabs` bar (`App.tsx:3436-3452`): at eight ports the labels (e.g. "Port of Gothenburg 2026") scroll off-screen behind scroll arrows on tablet widths. There is no ranking/sort and no compare-subset default — the checkbox list renders all loaded ports (`App.tsx:2823-2831`) and the fresh-load comparison selects all of them (`comparisonSelection` initialized to `LOADED_PORTS.map(...)` at `App.tsx:3359-3361`), so the default view at eight ports is the worst case of every problem above. The ranking integrity path (`rankByConvertedBasis`, `web/src/conversion.ts:89+`) is generic over ports and survives expansion; the cheapest/most-expensive markers do not. Details in item D.

## Audit item A — Port-count implicitness sweep

Every site where the number three or a specific port identity is implicit or explicit in code rather than data. Locations are exact; each carries the smallest change that would generalize it (**recommendation only — nothing was implemented**).

### A1. `defaultCall` per port — a hardcoded enumeration in core code

- **Location:** `core/src/defaults.ts:30-136` — `defaultCall(portId)` returns one shared default object, then spreads port-conditional blocks: `...(portId === 'gothenburg' ? { towage_cost_per_tug: 60000, tug_count: undefined } : {})` (`defaults.ts:90-92`), `...(portId === 'helsingborg' ? { issc_valid: true, ees_rate_per_move: 35, ... } : {})` (`defaults.ts:102-108`), `...(portId === 'hamburg' ? { terminal_operator: 'HHLA', engine_tier: undefined, ... } : {})` (`defaults.ts:109-135`).
- **What it assumes:** that the set of ports and their port-specific default inputs are known at code-write time. Adding port #4 with any port-specific input (a CSI class, an EES level, a terminal operator, a default tug cost) means editing this function; forgetting to edit it means the port silently gets none of its list-price defaults (the exact defect class the v0.2.53 shared-call fix repaired for the comparison — spec changelog row 0.2.53, item 1). Every downstream consumer inherits the assumption: the web fresh-load call (`web/src/App.tsx:3357`), the port-switch reset (`App.tsx:3375-3388`), and the comparison's per-port merge (`App.tsx:2428-2441`).
- **Smallest generalizing change:** move the per-port blocks into a per-port defaults section of each port's YAML (configuration-only values, not rates — the same boundary the OPS descriptor debates in A2), and have `defaultCall` read them; the function keeps the shared worst-case core and overlays the port's declared defaults. Cost: touches `core/src/defaults.ts`, `core/src/loader.ts` (validation of the new section), every YAML file once (adding the section for the three current ports, byte-equivalent values), the `environmental_defaults` / `engine_repairs` / web `comparisonDefaults` and `profileSeeding` pin suites (defaults are pinned figures — the zero-drift baselines prove the values survived the move), and the spec (a defaults contract paragraph; figure-neutral so the changelog row would state zero drift).

### A2. `opsComponentsForPort` (core/src/engine.ts) — the v0.2.57 per-port switch in engine code

- **Location:** `core/src/engine.ts:1536-1557` — `OPS_COMPONENTS_BY_PORT: Record<string, OpsComponentsSpec>` with literal keys `gothenburg` / `hamburg` / `helsingborg`, each entry four `{ enabled, currency, unit }` descriptors (SEK at `engine.ts:1537-1540`, EUR at `:1543-1546`, SEK at `:1549-1552`); `opsComponentsForPort(portId)` at `engine.ts:1555-1557` returns `OPS_COMPONENTS_BY_PORT[portId] ?? OPS_COMPONENTS_BY_PORT.helsingborg` — the **fallback is a named port**: an unknown port silently receives Helsingborg's all-four-open posture, which for a port that publishes, say, an electricity-only OPS fee would render speculative input boxes that port's tariff contradicts.
- **What it assumes:** the per-port OPS shape is code knowledge, enumerated over exactly the three current ports, with Helsingborg as the least-defined default.
- **Data-driven feasibility without breaking the "never in ports.json" pin:** feasible, and the descriptor is the right candidate — it is configuration, not rates (presence, currency, unit; the spec v0.2.57 row itself says "This is web-layer configuration in spirit but lives beside the single calculation path"). Two routes: (a) a per-port YAML section (e.g. `ops_speculative:` with the four components' enabled/currency/unit), carried through the conversion script like any other metadata — this puts the descriptor in the same YAML that is the port's source of truth and keeps it out of any rate table; the "never in ports.json" pin's *intent* is that no OPS rate ever ships in the registry, which a presence/currency/unit block does not violate, but its *letter* (the v0.2.57 spec text: "the numbers living only in the call input and never in ports.json or any rate table") would need one clarifying sentence. (b) A separate core-side config file (e.g. `core/data/ops_postures.yaml`) keyed by port id — zero change to ports.json at all, at the cost of a second per-port file to maintain. Recommendation: **route (a)**, with the fallback changed from `?? OPS_COMPONENTS_BY_PORT.helsingborg` to a declared-everywhere default (electricity-only, the most common published posture) or an explicit loader error for a port with no section — never a silent named-port fallback. **Whether the pin itself should be revised is a question for a future directive, not this audit**; the record here is that the pin's intent (no OPS *rates* in the registry) survives either route, and the spec sentence "never in ports.json" would need revising under route (a) only. Cost: `core/src/engine.ts`, `core/src/loader.ts`/`types.ts` (schema), the conversion script (already generic), the three YAML files once, the web `opsSpeculative` suite (15 pins render per-port shapes), the core engine pins on `opsComponentsForPort`, and the spec §4.2.4 paragraph.

### A3. `PORT_SPECIFIC_CALL_FIELDS` and the currency conventions (SEK Sweden / EUR Hamburg)

- **Location 1:** `web/src/App.tsx:3324-3341` — the array of 33 port-specific input field names, enumerated by hand; consumed by the port-switch reset (`App.tsx:3379-3381`) and the comparison's per-port default merge (via `defaultCall`, `App.tsx:2428-2441` with the explicit comment at `:2428` naming it). Adding a port with a new port-specific input means appending to this array and adding the field to `defaultCall` — two hand-kept lists that must agree or a field stops resetting (silent staleness, the same shape as the v0.2.53 defect).
- **Location 2:** currency per port is hardcoded in four places: `core/src/engine.ts:72` (`currency: Currency = 'SEK'` — the FeeResult default), `engine.ts:1537-1552` (OPS descriptors), `web/src/conversion.ts:63-77` (`toComparisonBasis`: `'SEK'` returns unconverted, `'EUR'` converts, **any other currency returns unconverted with `converted: false`** — a DKK port would render native-primary with no converted basis while still being numerically ranked against SEK in `rankByConvertedBasis`? No — verified: `rankByConvertedBasis` (`web/src/conversion.ts:89+`) orders by the converted basis, so a DKK port would sort as an unconverted DKK amount against SEK amounts, a cross-currency comparison on raw amounts, violating the spec §6 contract silently), and `core/data/exchange_rates.yaml` (exactly one rate: EUR→SEK 11.275). The SEK-comparison-basis contract itself (spec §6) is written as if "Swedish ports + Hamburg" were the universe.
- **What it assumes:** exactly two currencies exist (SEK, EUR) and exactly one conversion (EUR→SEK). Gdansk (PLN) or Aarhus (DKK) — both in the spec §9 initial set — break `toComparisonBasis`'s silent third branch and the exchange-rate data model in one step.
- **Smallest generalizing change:** for the field list — derive `PORT_SPECIFIC_CALL_FIELDS` from `defaultCall`'s port-conditional keys (or the A1 YAML section) rather than maintaining a second array; for currency — generalize `toComparisonBasis` to convert *any* non-basis currency through the resolved rate table (falling back to unconverted only when no rate exists, with a visible flag per the §6 fallback convention), and let `exchange_rates.yaml` carry N rates toward the comparison basis (SEK). Cost: `web/src/conversion.ts` + its 6-test suite, `web/src/App.tsx` (array removal), `core/data/exchange_rates.yaml` + the loader/validation pins on it, the web `conversion`/`comparisonDefaults`/`chargeTypeStages` suites (converted-figure pins are EUR-specific today), the spec §6 currency contract paragraph, and the accessibility pin at `web/src/accessibility.test.ts:74` (asserts the kr-per-EUR label). The ranking-integrity contract (spec §6, `rankByConvertedBasis` pins) is the safety net: any generalization must keep every cross-port ordering on the converted basis.

### A4. Terminal operators, input sections per port, arrival-origin/vessel-profile wiring, the comparison's port column enumeration

- **Terminal operators:** `web/src/App.tsx:1383` — the Hamburg Terminal Operator select hardcodes two `MenuItem`s (`HHLA` / `Eurogate`) with inline labels; the gate values themselves live in data (`terminal_operator` conditions in `hamburg_2026.yaml`), so a third Hamburg operator (Rhenus Midgard, Unikai — both named in spec open item 4) is a UI edit. The default `'HHLA'` is hardcoded twice more (`App.tsx:1378` fallback `state.call.terminal_operator || 'HHLA'`, `core/src/defaults.ts:112`). Smallest change: render the operator options from a biller/operator list in the port data (the billers section already exists per port), keeping HHLA as a declared default. Cost: the `terminalScope` web suite (7 pins assert both labels), `defaults.ts`, the YAML billers block, spec §4.4.2 terminal-scope paragraph.
- **Input sections per port in App.tsx:** the per-port workspace gates five JSX blocks on port id: `port.metadata.id === 'hamburg'` (build-year field, `App.tsx:969`; the Hamburg call-parameters card, `:1368-1660` region), `=== 'gothenburg' || === 'helsingborg'` (CSI class select, `:1157`), `=== 'gothenburg'` (ancillary services card, `:1257`), `=== 'helsingborg'` (call-parameters card, `:1660`). Each new port with any port-specific input means another gated block in an already 3,482-line file — the A1/A3 generalizations (data-declared defaults plus data-declared operator lists) remove the *values*, but the *input widgets* (a select with helper text citing tariff clauses) are inherently per-port surface. Smallest change that scales: per-port input-section components (item B's decomposition) fed by a data-declared input list; anything less just relocates the switch. Cost: every web suite that renders a workspace (`vesselSelection`, `tierField`, `tierWiring`, `layTime`, `envGuidance`, `opsSpeculative`, `wasteOrigin`, `summaryTheme` — 8 suites read or render these blocks); the source-reading pins among them (item B) would need re-pointing.
- **Arrival-origin wiring:** the selector is shared and generic (`App.tsx:1088-1100`; two MenuItem values, outside-europe/europe; default in `core/src/defaults.ts:56-58`; context-strip rendering at `App.tsx:2909-2918`). The *values* are the Gothenburg waste dimension, but the input is not port-gated and ports without origin-gated rules simply ignore it. **No three-port assumption** — this one survives expansion as-is; the deferred rotation-mode override (deferred queue) is the only per-port-identity question, and it is already recorded.
- **Vessel-profile wiring:** `core/src/vessel_profiles.ts` is port-agnostic (profiles key on vessel identity/class, not port; `defaultProfile()` at `defaults.ts:30-38` via `defaultProfile()` — no port condition anywhere in the module, verified). The lay-time/productivity comments reference "Gothenburg-class productivity" (`App.tsx:2946-2947`, `profileSeeding` pins) — prose, not a gate. **No port-count assumption.**
- **The comparison's port column enumeration:** fully generic — columns render from `portResults.map` (`App.tsx:3041-3055` header, `:3098+` cells), selection from `selectedPortIds`, and no site in `ComparisonView` names a port. The three-port *shape* is data-driven; the costs of more columns are layout, not enumeration (item D).

### A5. The comparison view: does it render all ports unconditionally, and what breaks at five or eight?

- **Rendering:** conditional on selection only. The checkbox list renders all loaded ports (`App.tsx:2823-2831`), the fresh load selects all (`App.tsx:3359-3361`), and `portResults` prices every selected port (`:2428-2441`). Nothing hardcodes three. The "prices one identical call at all three ports" prose (`App.tsx:2842-2845`, spec §4.4.2 comparison philosophy) is the only place the number three is *written* into the surface — a prose staleness at port #4, not a break.
- **What breaks at five/eight:** (1) *Column count vs width* — the desktop table is `width: 100%` with no per-column `min-width` and no column-count breakpoint (`web/src/index.css:838-841`); the fit contract's `nowrap` spans (`.comparison-figure`, `index.css:853`) mean each column's floor is its widest figure (native amount + converted secondary + per-GT line, now three stacked lines per Grand Total cell since v0.2.58). At eight ports on a 1366px viewport the container's `overflow-x: auto` (`index.css:833-835`) makes the whole comparison a horizontal scroll — usable but no longer a side-by-side reading surface, which is the comparison's entire purpose. (2) *Mobile card stack* — one card per port below 600px (`responsive.ts:22`, `App.tsx:2943-3012`), linear flex column (`index.css:1080-1084`); eight cards × (Grand Total + 3 stage rows + 3 charge-type lines + N family lines + 4 subtotals) is a very long scroll with no way to collapse or subset. (3) *The per-GT row* — `grandTotalPerGtCell` (`App.tsx:2772-2810`) is per-column and generic; it does not break, but it *adds* a stacked line to every column, worsening (1); the desktop table's per-GT figure is the widest cell content. (4) *Row count* — the stage/charge-type/family row set is per-port-families ∪ across ports (`rowsByStage` memo, `App.tsx:2560-2648` region): each added port's unique fee families add rows, so the table grows in both dimensions; the structural-presence suite's per-port loops grow accordingly (item C).
- **Smallest generalizing change:** a compare-subset control defaulting to a bounded selection (e.g. first 4) plus a column-count breakpoint that swaps the table for the card stack (or a horizontally scrollable pinned-label table with explicit `min-width` per column, making the scroll deliberate rather than emergent). Cost: `App.tsx` comparison JSX, `index.css` comparison block, the `responsive` suite (34 pins include table/card branch assertions), `structuralPresence` (7 pins assert desktop-table DOM), `chargeTypeStages` (18 pins render the desktop table), `grandTotalPerGt` (10 pins, both surfaces), `comparisonDefaults` (11), `cardSpacing` (6), `accessibility` (desktop/cards aria pins). This is the highest-pin-count surface in the repository — item B's map is the scoping instrument.

### A6. Port selection UI: what does the user click today, and what does it become at eight ports?

- **Today:** a persistent scrollable MUI `Tabs` bar, one tab per loaded port plus a fixed "Compare Ports" tab (`App.tsx:3436-3452`), `variant="scrollable" scrollButtons="auto"` (`App.tsx:3445`); tab index derived from `LOADED_PORTS` order (`App.tsx:3400-3406`); the comparison's port-selection checkboxes (`App.tsx:2823-2831`). At three ports the bar reads at a glance.
- **At eight ports:** eight "Port Name 2026" labels (the `portLabel` format includes the year, `App.tsx:2359-2361`) do not fit a tablet or laptop width; `scrollable` hides them behind arrow buttons, which is discoverable but makes port-to-port jumping a scroll-gesture each time, and the current port can sit off-screen (the active tab auto-scrolls into view only on selection via MUI internals). The comparison checkbox list at eight ports is an eight-item unlabeled column of long labels — workable but unsorted and unsearchable.
- **Smallest generalizing change:** at ≤5 ports keep the tab bar; above that, a compact dropdown/combobox (the vessel select at `App.tsx:818` is the in-repo pattern to mirror — searchable `Autocomplete`), with "Compare Ports" as a persistent action beside it. Cost: `App.tsx` nav block, the `vesselSelection`/`responsive` suites that query the tab/nav DOM (`vesselSelection.test.tsx:339-342` pins the header; the tabs are queried by role in several render tests), `accessibility` pins on the nav, and the spec §4.3.1 multi-port-navigation paragraph. Also the only place `LOADED_PORTS[0]` is the implicit default port (`App.tsx:3345`, `:3357`, `:3359`) — first-loaded YAML wins the fresh-load page; stable but worth stating in the spec when ports multiply.

## Audit item B — App.tsx decomposition map

`web/src/App.tsx` is 3,482 lines holding: the theme hook and MUI bridge, vessel presets/options, the per-port workspace (inputs + results, ~1,900 lines), the comparison view (~950 lines), shared renderers, and the App shell. Proposed boundaries, which pins read App.tsx source, and which prove behavior-neutrality:

### Proposed component/module boundaries

1. **`web/src/theme.ts`** — `useAppTheme`, `muiThemeFor`, `__setMobileQueryForTests` (`App.tsx:111-185`). Consumers: theme tests (`theme.test.ts`), responsive suite's mobile hook override.
2. **`web/src/vesselOptions.ts`** — `VESSEL_PRESETS`, `GENERIC_SIZE_CLASS_LABELS`, the `VesselOption` union, `vesselOptions()`, labels (`App.tsx:293-350`), plus `customVesselLabel`. Pinned by `vesselSelection` (both source and DOM pins).
3. **`web/src/portWorkspace/`** — `PortWorkspace` split by contract surface: `InputSections` (shared general-information group, `App.tsx:979-1155`; the five port-gated blocks per A4), `OpsInputs` (the descriptor-driven OPS group, `App.tsx:1735-1830`), `ResultsBlocks` (total strip `App.tsx:747-830`; cost breakdown + zero-collapse + fee lines + derivation, `App.tsx:1940-2350`), `WorkspaceShell`. The `SEGMENTS` constant (`App.tsx:248-262`) and `WASTE_COMPULSORY_RULES` (`App.tsx:285-289`) move beside their consumers.
4. **`web/src/comparison/`** — `ComparisonView` split into: `ComparisonModel` (the `portResults`, `rowsByStage`, `ranking` memos — pure functions over engine results, the natural unit for behavior pins), `ComparisonTable` (desktop), `ComparisonCards` (mobile), `ComparisonContextStrip`, `ComparisonControls` (selection + disclosures), and the shared cells.
5. **`web/src/comparison/cells.tsx`** — `amountCell` (`App.tsx:2653-2731`), `convCell` (`App.tsx:2732-2770`), `grandTotalPerGtCell` (`:2772-2810`), `portLabel`. These are the shared renderers the directive names; they close over `rateInfo`, `isMobile`, and the disclosure states, so the module boundary is *props-in* (rate info, visibility flags), not a hook-free extraction.
6. **`web/src/appShell.tsx`** — the `App` component: page state, the shared `vessel`/`call` state, `PORT_SPECIFIC_CALL_FIELDS` reset effect (`App.tsx:3373-3388`), nav tabs (`App.tsx:3436-3452`), `LOADED_PORTS`/`LOADED_VESSELS` registries (`App.tsx:102, :237`).

### Pins that read App.tsx source via fs.readFileSync, and where they re-point

Ten suites read `App.tsx` as text (`grep -rn "readFileSync.*App.tsx" web/src`): `accessibility`, `chargeTypeStages`, `comparisonDefaults`, `conversion` (3 tests), `derivation`, `grandTotalPerGt`, `profileSeeding`, `responsive`, `summaryTheme`, `vesselSelection`. Re-pointing by proposed module: theme/nav/markup pins → `appShell.tsx`; workspace-input pins (tier field text, lay-time label count, aria on fee derivations, `Vessel Summary` absence) → `portWorkspace/*`; comparison pins (aria-controls ids, stage-row classes, not-levied wording, `grandTotalPerGtCell` presence, the flat-rate basis-dedup excerpt at `grandTotalPerGt.test.tsx:203-207`, `conversion.test.ts:166-177`'s PortWorkspace-slice assertion that the workspace contains no converted markers) → `comparison/*` / `portWorkspace/*`. Two structural source pins need explicit care: `conversion.test.ts:166-177` slices App.tsx between `indexOf('const PortWorkspace')` and `indexOf('const ComparisonView')` — the slice boundaries are module names, so the extraction preserves the assertion's *intent* but must re-express it as "the workspace module imports no `toComparisonBasis`"; `profileSeeding.test.tsx:82-117` pins exact `useState`/`seedProfile` source shapes that live across the workspace/shell boundary (the seeding state belongs in the shell; the helper text pins belong to the workspace inputs).

**Source-coupled vs behavior-coupled:** source-coupled pins (text/regex assertions on App.tsx: ~60+ across the ten suites) must be re-pointed but prove nothing about behavior; behavior-coupled pins (DOM assertions via `render`: `structuralPresence` 7, `chargeTypeStages` 18, `comparisonDefaults` 11, `grandTotalPerGt` 10, `responsive` 34, `cardSpacing` 6, `opsSpeculative` 15, plus the rendering halves of the source suites) survive a pure move untouched and are the actual proof.

### Which pins prove the refactor behavior-neutral (the zero-drift safety net)

- **The three zero-drift baselines** — GOT 3,007,051.15 SEK / HAM 2,313,489.31 EUR / HEL 8,481,257.40 SEK under the default Maren Maersk call — pinned in `comparisonDefaults.test.tsx:203-207` (all three ports through the comparison's merged per-port defaults path), `profileSeeding.test.tsx` (GOT default), `grandTotalPerGt.test.tsx` (per-GT arithmetic per port), and `core/test/derivation_exposure.test.ts` (core-side default totals). These prove the *computation* is untouched: the memos, the per-port default merge, the engine path.
- **The sum-of-lines invariant** (visible lines + suppressed zeros = Grand Total, all ports, both Hamburg operators; `chargeTypeStages` 18-pin suite) proves the comparison's row assembly — the highest-risk extraction, since `rowsByStage` is the memo most likely to be rewritten during decomposition.
- **The structural-presence suite** (7 DOM-order pins: stage rows in canonical order, Grand Total beneath stages, charge-type nesting, mobile card lines/wording/storage re-activation) proves the rendered *structure* — the cheapest full-surface proof that the JSX move changed nothing.
- **The mobile/desktop branch pins** (`responsive` 34: card-first-element Grand Total at both viewports, table hidden below 600px via `index.css:1252-1255`, conversion disclosure behavior) prove the `isMobile` branching survived the prop-ization of the cells.
- **The converted-figure and per-GT pins** (`grandTotalPerGt` 10, `conversion` 6, the EUR-path pins inside `comparisonDefaults`) prove `convCell`/`grandTotalPerGtCell` extraction kept rate handling and the mobile collapse intact.
A refactor pass that keeps all of the above green without editing a single expectation is behavior-neutral by construction; every *edited* expectation must be named and classified (the repo's standing re-pin convention, e.g. the v0.2.56 responsive-suite re-pin precedent).

## Audit item C — Data-pipeline expansion cost

**What one new port requires, end to end (verified against the three-port reality, not the README's claim):**

1. **Source acquisition + extraction reference:** archive the tariff PDFs under `docs/sources/<country>/<port>/`, write `<PORT>_EXTRACTION_REFERENCE.md` (the per-tariff audit record; the three existing ones are 15-20k words each — the Gothenburg one carries the verbatim quotation discipline the v0.2.53 cargo-due adjudication used). This is the dominant cost and it is *human* work, not code.
2. **YAML authoring:** `core/data/<port>_<year>.yaml` — metadata, billers (each with currency), fee rules with source references. Schema is fully per-port generic (verified: no port id appears in `loader.ts`/`types.ts`; `hamburg_2026.yaml` shows the multi-biller pattern). **Plus the four code sites from item A**: `defaultCall` block, `OPS_COMPONENTS_BY_PORT` entry (or the generalized data section), `exchange_rates.yaml` rate if a new currency, and per-port input widgets in the workspace. This is the audit's headline finding: the README's "adding a port never requires a code change" is true of the *rule engine* and false of the *defaults/OPS/currency/input-form* perimeter.
3. **Classification coverage sweep:** `core/src/classification.ts` — every rule id needs a functional class, either via the shared Swedish patterns (`classifyRule`, `core/src/classification.ts:633-670`) or a new per-port table (`PORT_FUNCTIONAL_CLASSIFICATION`, `classification.ts:624-628`). The completeness test (`functional_classification.test.ts:39-56`) hardcodes the file list (`:40-43`) — **a per-port list that must be extended per port**; at eight ports this and its siblings (`handling_hygiene.test.ts:172,180`'s `[gothenburg, hamburg, helsingborg]` arrays, `health_check.test.ts`'s `TOWAGE_RULE_IDS` map at `:26-29`) are hand-edited per-port loops, linear not combinatorial, but each miss silently skips coverage rather than failing.
4. **Baseline pinning:** worked-example pins per the pin-source hierarchy (spec §7, v0.2.37), default-call total pins (the new port's analogue of the three baselines), and the classification/estimate pins. Cost scales with the tariff's published worked examples (Gothenburg's lathund rows were the richest source; a port with no published examples pins at extraction-reference level, the weaker precedence tier).
5. **ports.json regeneration:** `node core/scripts/convert_yaml_to_json.js` — fully generic (scans `core/data/*.yaml`, emits ports/vessels, rewrites source URLs; `convert_yaml_to_json.js:8-19`). Zero cost, but the generated file is gitignored and regenerated per build — a new port appears in the UI only after this step, worth stating in any port-addition runbook.
6. **Spec sections:** a §5.x port-file contract section (Hamburg §5.3 and Helsingborg §5.4 are the templates), changelog row (version guard demands it — any `core/data/` touch triggers it), possibly §6 (new currency), §4.3.1 prose (the "all three ports" phrasing), and the §9 initial-port-set list.

**Pass cost of one new port, in the unit of prior passes:** **audit-heavy at the front, implementation-heavy in the middle, verification-dominated at the tail — the same shape as the v0.2.49 Hamburg terminal-scope pass, at roughly 1.5-2× its size.** The extraction reference is audit-heavy (tariff reading, quotation discipline, adjudications like the cargo-due one); the YAML + four code-site edits are implementation-heavy but bounded; the pinning and per-suite per-port loop extensions are verification-dominated (the v0.2.53 Helsingborg pass — nearest single-port analogue — added 10 core + 9 web pins and re-verified every standing audit item; expect ≥ that for a port with a novel currency or operator structure).

**Combinatorial vs linear growth:** the comparison pins that render all ports are the one combinatorial risk. `structuralPresence` (7 pins) and `chargeTypeStages` (18 pins) currently assert structures *per port in loops over LOADED_PORTS* (`chargeTypeStages.test.tsx:246`, `comparisonDefaults.test.tsx:105,173,209,220`) — these are linear (O(ports) assertions, fine at eight), but their *fixture cost* is not: each render prices N ports, and jsdom render time for `ComparisonView` grows with columns; `terminalScope`/`vesselSelection`/`responsive` render full workspaces whose input-form size grows per port-gated block. The genuinely multiplicative surface is **the desktop comparison DOM at all-selected ports**: every suite that renders `ComparisonView` with `selectedPortIds={LOADED_PORTS.map(...)}` (11 suites, per the `grep` at item A5) renders N columns × M rows; at eight ports that is ~2.7× the DOM of three ports per render, across ~60 rendering tests — suite wall-clock grows superlinearly in practice while assertion count stays linear. **Restructuring needed:** (a) the per-port hardcoded lists (`functional_classification.test.ts:40-43`, `handling_hygiene` arrays, `TOWAGE_RULE_IDS`) should derive from the loaded registry (they exist to be exhaustive, and exhaustiveness by enumeration is exactly what fails silently); (b) the all-ports comparison renders should adopt a bounded default selection (which item D recommends for the UI anyway — the pin suites then follow the product decision rather than fighting it); (c) per-port comparison pins should keep looping over LOADED_PORTS (linear) rather than being duplicated per port (quadratic in maintenance).

## Audit item D — UI scalability findings (five to eight ports)

1. **Table width (desktop).** Finding: no per-column min-width or column-count breakpoint (`index.css:838-841`); at 5 ports the converted-secondary + per-GT lines likely still fit ~1280px; at 8 they will not — emergent whole-container horizontal scroll (`index.css:833-835`) breaks the at-a-glance side-by-side reading. Recommendation: a ranked/pinned-label table with explicit per-column `min-width` (deliberate scroll) up to a breakpoint, and beyond it either a default compare-subset (see 3) or a compact card grid. Surfaces/pins: `index.css` comparison block; `comparison-table-container` hidden below 600px (`index.css:1252-1255`) is asserted by the `responsive` suite; stage-row order, nesting, and wording by `structuralPresence` (7) and `chargeTypeStages` (18); per-GT lines by `grandTotalPerGt` (10); theme discipline by the class-level pins in `summaryTheme`/`chargeTypeStages` (any new CSS must keep color literals inside `:root`).

Recommendation: default the mobile comparison to a smaller subset (2-3) with the checkbox list immediately available; optionally an accordion collapse per card. Surfaces/pins: `App.tsx:3359-3361` (selection init — behavior change, needs a spec row), the card JSX (`App.tsx:2943-3012`), `cardSpacing` (6 rhythm pins), `responsive` (card-first-element Grand Total pins, conversion-disclosure pins), `structuralPresence` mobile pins (wording, storage re-activation), `accessibility` card aria pins.
3. **Ranking / subset control.** Finding: no sort, no ranking display beyond the two cheapest/most-expensive markers (`App.tsx:3048-3056` header cells; card markers at `App.tsx:2960-2965`), and at 5+ ports "cheapest/most-expensive" leaves 3-6 unranked middle ports; the v0.2.39 ranking strip was *removed* as duplication (spec v0.2.47 changelog) — at eight ports that rationale inverts (two markers on an eight-column table no longer carry the ranking). Recommendation: a compare-subset control (checkbox list is present but all-on by default; make the default bounded) and an optional rank-ordering of columns or a small ranked strip, on the converted basis per the §6 contract. Surfaces/pins: `ComparisonView` controls + table header; the removal pins at `accessibility.test.ts:129-131` assert the ranking strip's *absence* — they would need re-pointing (named re-pin, precedent standing); `conversion` suite's ranking pins (the pure function) unchanged; `comparisonDefaults` zero-drift pins unchanged (ranking is display-only).

## The two questions, answered plainly

**"Is the code optimized enough to handle more data sets?"** — The engine/data core: yes, genuinely (per-port-generic loader, classifier patterns, conversion script, comparison memos; verified, not just claimed by the README). The defaults/OPS/currency/input perimeter: **no** — four enumerated sites (`defaultCall`, `OPS_COMPONENTS_BY_PORT` with its named-port fallback, `toComparisonBasis`'s two-currency assumption + single-rate `exchange_rates.yaml`, and the port-gated input JSX) each demand an edit per port, per operator, or per currency, and two of them (`defaultCall`/`PORT_SPECIFIC_CALL_FIELDS`, the silent unknown-currency conversion) fail *silently* when the edit is forgotten — the same defect class this repository has already had to repair once (v0.2.53). Adding ports 4-5 without generalizing is survivable; adding 6-8 multiplies the silent-failure surface every time.

**"Is the UI workable at more ports?"** — **At five: degraded but functional** (tab bar scrolls, table likely scrolls at narrow desktop widths, mobile card stack long). **At eight: no** — the all-ports-by-default comparison (both the fresh-load selection and the unbounded checkbox list) makes the worst case the default; the table loses its side-by-side purpose to horizontal scroll; the mobile stack becomes an unsorted 8-card wall; the two ranking markers leave most ports unranked. The fixes are known, bounded, and enumerated in item D with their pin costs — none requires engine or data change; all are presentation-layer under the existing contracts.

## Recommendation on sequencing: refactor-first, then ports — with one split

**Argument:** the two questions have different failure modes. The *data pipeline* can absorb ports 4-5 without any refactor (each addition costs the four enumerated code-site edits, which are annoying but bounded and loud). The *UI* cannot absorb ports 6-8 without the item D work, and — more decisively — the *refactor itself* gets more expensive with every port added: the decomposition (item B) must re-point ~10 source-reading suites whose per-port loops and per-port fixture blocks grow with each port; doing it at three ports is the cheapest it will ever be, and the zero-drift baselines (three pins) plus the sum invariant and structural suites give it the strongest behavior-neutrality proof it will ever have. The same is true of the A-item generalizations: `defaultCall` and the OPS descriptor generalize over *three* entries today; over eight, any generalization risks eight-way re-pinning instead of three-way. Sequencing: (1) the App.tsx decomposition (behavior-neutral, pin-preserving — the B map is its scope); (2) the A-item data-driven generalizations (defaults, OPS, currency/rates, operator list — each its own zero-drift pass); (3) the item D UI scalability features (each presentation-only, each re-using the now-modular comparison components); (4) then ports 4-8 land as *data* passes with the README's claim finally true. The one split: a single new port with no new currency and no novel input widgets (e.g. a second Swedish port) can land *before* the refactor without penalty — the enumerated edits are the same three-site edits the Helsingborg pass already made once; anything with a new currency or operator structure should wait for step (2), because it is exactly the silent-failure surface.
