# Port Call Cost Analyzer — Specification v0.2.66

This document is the committed record of the project specification at version 0.2.66. It is the sole governing authority for the data model, engine, and UI contracts of the Port Call Cost Analyzer. `docs/INTENDED_STATE.md` was refreshed at v0.2.55 from the Gothenburg-only pilot's claimed authority to an audit concordance: it records the repository structure, the three-port reality, and the historical verification checkpoints that the test suite pins, and where the two documents overlap, this specification governs.

## Versioning Policy

This specification uses three-decimal semantic versioning:

- **Major (X.0.0):** Fundamental architectural changes, scope redefinitions, or backward-incompatible revisions to the data model or output contract.
- **Minor (0.Y.0):** New features, new sections, or substantively new decisions that do not break existing structure. May also jump by more than one (e.g. 0.2.0 to 0.5.0) when a batch of related changes lands together.
- **Patch (0.2.Z):** Corrections, clarifications, wording harmonisation, and small factual adjustments that do not add or remove structural elements.

Small adjustments increment only the third decimal. Larger updates may jump more than one increment in the second decimal. Major version increments are reserved for genuine architectural breaks.

## 1. Purpose

A tool that estimates and compares the total publicly-known cost of a container vessel call across European ports, given a vessel profile and call parameters. Each result is traceable to its source tariff and validity date. The application is a static bundle deployable to any static host; the hosting target is an owner choice, deliberately unspecified here.

**Important scope note:** terminal handling charges may be confidential or contract-based at some ports. The tool therefore attempts port dues, nautical services, statutory/ancillary fees, and — where publicly available — terminal operator charges, and labels coverage explicitly per port rather than claiming a true "total" cost. Where a terminal publishes rates but shipping lines may hold different contract rates (e.g. APMT Gothenburg handling charges), the tool displays the published rate with a contract-vs-published caveat rather than a data gap.

## 2. Core Architecture Principle

**Ports are data, not code.** The application contains a single generic rule-evaluation engine. Every port's costing model — including its unique fee structures — is expressed as data in a structured port file. Adding or revising a port's tariff (for example, Hamburg's 2024 reform from a shipping-area split to progressive GT bands) is a data edit, never a code change.

**Each port is a self-contained costing model** that produces results under a shared output contract, enabling an aggregation layer that ranks and compares any one call across ports uniformly.

## 4. Tariff Rule Language

### 4.1 Charging Entities (Billers)

A port is not a single biller — a call generates a cluster of costs from multiple parties. Each fee rule belongs to a charging entity (biller), of five kinds:

1. Port authority — port dues and general infrastructure charges (as in Hamburg).
2. National or state authorities — e.g. Sjöfartsverket (Swedish Maritime Administration), which levies Swedish fairway dues (*farledsavgift*) independently of the port authority.
3. Terminal operator(s) — lifts over quay, storage, and related cargo charges charged to the vessel. Large ports such as Hamburg have multiple container terminal operators, each with its own tariff.
4. Independent service providers — pilotage, towage, mooring, waste, etc.
5. Other costs — a catch-all for charging entities not yet classified, since port clusters are complex and additional actor types may emerge during extraction. An item assigned to "other costs" must carry a free-text biller name and triggers a quality warning.

Ports vary enormously in structural complexity, and the model must embrace that asymmetry rather than normalize it away:

- Hamburg (complex): port authority charges banded port dues, OPS charges, and infrastructure/fairway fees; multiple terminal operators each levy their own lift and storage tariffs. A call's cost depends on which terminal the vessel calls at.
- Helsingborg (simple): a flat-rate port dues structure from the port authority, whose own company also operates the terminal — a single biller, few rules.
- Gothenburg (intermediate): banded port dues from the authority, plus *farledsavgift* levied separately by Sjöfartsverket, with separate terminal arrangements.

A port file contains one or more billers, each with its own fee rules, currency, and tariff documents. The comparison output presents costs grouped by biller within each port, then a port total, so the user sees who charges what. Where a terminal operator's charges are not public, the gap is shown explicitly ("terminal charges: not publicly available — confidential") rather than omitted, so simple ports are not unfairly advantaged in comparison.

### 4.2 Cross-Port Comparability: Function vs. Biller

The same underlying cost function may be carved up differently across ports and countries:

- Fairway or fairway maintenance: a separate state-authority charge in Sweden (*farledsavgift*, Sjöfartsverket); an infrastructure charge from the port authority in Hamburg; folded into general port dues elsewhere.
- Towage and other nautical services: provided and billed by independent commercial providers in some ports, by the port authority or its subsidiary in others, with differing pricing structures.
- Sweden is the notable case of a national authority levying charges outside the port structure, but analogous structural variation exists elsewhere.

The model therefore separates two orthogonal attributes on every cost item:

1. fee_family — the economic function (fairway, towage, port_dues, ...), assigned consistently across all ports and countries. This is the semantic key that makes cross-port comparison meaningful.
2. biller — the factual attribution of who actually levies the charge in that port. This is always recorded as it is in reality, never normalized.

Two ports can therefore show the same fee family with entirely different billers, rate structures, and even embedded-in-another-charge status. The latter is recorded via a bundled_into marker on cost items subsumed within another fee, so that a function folded into port dues is visible rather than silently omitted or double-counted. Comparisons operate at the level of economic function, while the drill-down detail preserves exactly who charges what, where.

### 4.2.1 Cost-Segment Grouping: Vessel Call, Energy at Berth, Terminal and Yard

Every fee family maps to one of three cost segments, derived in the presentation layer (never stored per-rule in the data layer, to avoid a redundant attribute that could drift):

- Vessel call (the coming and going of the vessel, through to boxes at place of rest): port_dues, environmental_surcharge, fairway dues and pilotage (Sjöfartsverket vessel/readiness/cargo fees, pilotage, ordering), waste, security (vessel-level), towage, mooring, anchorage, lay_up, connection_fee (non-OPS), terminal_handling (lifts over quay to place of rest), hatch_cover, gearbox_handling, cargo-side fees that bill per call unit (cargo_fee, frequency_discount).
- Energy at berth: the OPS component set (ops_connection, shore_electricity, ops_per_gt, ops_demand, ops_standby) or, when OPS is not used, at_quay_fuel — see 4.2.2.
- Terminal and yard (costs of dwelling in and moving through the terminal beyond place of rest): storage, yard_surcharge, gate_hazardous, idle_berth (when tied to cargo operations), security (per-unit, when yard-related), demurrage (cargo).

The cut within what was previously "cargo-side" is deliberate: the lift over quay to place of rest belongs to the vessel call (the call is not complete until the boxes are at rest), while yard moves, gate transfers, storage, and dwell-related charges are logistics decisions beyond the call itself. This serves the two distinct questions users actually ask — what does it cost to bring this ship here and work it, and what does it cost to hold and move this cargo through the terminal — which a single total conflates.

**Segment display names.** The three segments display as: "Vessel Call" (subtitled to note it includes terminal vessel operations — lifts on/off, hatch covers, gearbox), "Energy at Berth", and "Yard & Storage" (what happens to cargo after place of rest: storage, yard moves, gate, dwell). The third segment is deliberately not named "Terminal": the terminal's charges are split across segments by activity — terminal vessel operations belong to the vessel call, yard dwelling to this segment — and a biller-named label would misdescribe its contents. The by-biller view (Port of Gothenburg / Sjöfartsverket / APMT) is the place to see everything one biller charges. The internal mapping key remains `terminal_and_yard`; only display labels change.

**UI behavior.** The results view is organized as three toggleable segments. Layout is responsive to viewport class:

- Narrow viewports (phone): the segments render as a vertical stack, one section per segment — a long scrollable list.
- Wide viewports (laptop, desktop): segments render side by side in columns, with the column count adapting to both viewport width and the number of active segments, so that no panel falls below a readable width: two active segments sit side by side from ~1200px; three active segments require a wider viewport (~1600px) to sit three-across, otherwise the third wraps below the first row. Panels never shrink to overlapping or cramped widths to force a single row.

In either layout the segments are toggleable; any subset can be active; the expected common case is vessel call + energy (terminal and yard is rarely of interest and off by default for first view). Regardless of which pages are active or which layout applies, a persistent total strip is always visible, showing the grand total and the per-segment breakdown, so the full picture never requires switching views. Toggling pages filters the display only — it never changes what is computed or summed in the total.

Inputs that affect only one segment are grouped accordingly in the form (vessel particulars and call parameters vs energy inputs vs storage days and special-cargo details), with low-relevance inputs (e.g. flag state, which matters only for waste dues; storage days, which matter only for terminal-and-yard) demoted to an optional details section rather than sitting in the primary form. This is a presentation change only: the underlying data model and engine are unchanged, and all inputs remain available when relevant.

### 4.2.2 Energy at Berth: A Third Segment

Energy consumption at quay — OPS connection fees, shore electricity consumption, and at-quay fuel — is separated as a third cost segment, distinct from vessel-side and cargo-side, for two reasons.

First, economic: energy at berth is a different decision domain from port and nautical fees. Its cost scales with berth hours and vessel power demand rather than with GT, cargo, or call counts, and it is increasingly billed by a different party (the utility or port energy subsidiary, e.g. HPA Port Energy Solutions in Hamburg) rather than the tariff billers.

Second, regulatory: the EU regulatory framework makes this segment a forward-looking compliance cost rather than an optional service:

- AFIR (Regulation (EU) 2023/1804, Article 9 and Annex II) obliges TEN-T core and comprehensive ports to provide shore-side electricity for seagoing container and passenger ships.
- FuelEU Maritime (Regulation (EU) 2023/1805, Article 6) obliges container and passenger ships above 5,000 GT to connect to OPS (or use zero-emission technology) at TEN-T core maritime port berths from 1 January 2030; from 2025 to 2029, OPS energy is zero-rated under FuelEU (it does not count toward the ship's annual GHG intensity), serving as a connection incentive.

Consequence for the model: for calls dated 2030 or later at TEN-T ports, OPS usage should be treated as a default-on assumption with a visible regulatory notice (AFIR/FuelEU), rather than an opt-in input. The 2026 tariffs already carry related hooks: Gothenburg bills a 7,000 SEK OPS connection fee plus electricity — but only at Energy Port jetties 519–521 (tanker segment; no container OPS fee is published in the 2026 tariff, so container OPS pricing must be flagged as unpublished rather than defaulted); Hamburg grants an OPS discount of 0.015 EUR/GT on the port fee (through 31 December 2026) with electricity billed separately. Energy-at-berth charges carry their own fee families (ops_connection, shore_electricity, at_quay_fuel) so the segment derives mechanically from fee family, consistent with 4.2.1.

OPS pricing component set. OPS billing is not a single fee but a component set, differing by port and terminal. Each port file expresses whichever components that port actually publishes, as separate fee rules using the existing rate structures — no new rule types:

- Connection fee: flat, per call (ops_connection). Example: Gothenburg Energy Port, 7,000 SEK.
- Per-GT charge: rate per GT of the vessel, either as a separate OPS fee or as a port-dues surcharge/reduction tied to OPS use (ops_per_gt). Example: Hamburg's OPS discount of 0.015 EUR/GT on the port fee (a negative component).
- Energy charge: per kWh consumed, at a price that is market-dependent and therefore a user input at calculation time, not an encoded constant; the port file may record a reference price with a valid_from date and a quality flag noting volatility (shore_electricity).
- Demand charge: per kW or kVA of registered or metered peak demand, common where the utility bills capacity separately (ops_demand).
- Berth-hour or standby charge: per hour connected or per hour at berth with OPS available (ops_standby).

Rules of the component set: components are optional per port; absent components are simply not present rather than zero-valued; unpublished components are never invented (the Gothenburg container terminal, for instance, has no published OPS pricing at all, so a 2030 call there shows the mandate notice with the cost lines flagged unpublished). Where a port bills electricity through a separate energy subsidiary, the biller field reflects that entity. All components carry source references like any fee rule. Note (v0.2.32): as of the 2026 tariff set, no port publishes a per-kWh, demand, or berth-hour OPS component, so the only encoded energy-at-berth lever is the OPS connection toggle (Hamburg's per-GT rebate; Gothenburg's tanker-jetty connection fee); the kW/kWh/connected-hours inputs the v0.2.10 component set implies were deliberately absent from the form until a port actually published a rate that consumed them. Amendment (v0.2.57): the OPS speculative-input layer (section 4.2.4) re-introduces free-number kWh/price inputs as explicit user speculation — not as tariff-derived components; the tariff-traceability rule above is unchanged (no published rate is encoded as one), and the speculative inputs are deliberately outside the traceability contract.

### 4.2.4 OPS Speculative Inputs: User Speculation Outside the Tariff Contract

The model therefore gains free-number inputs for user speculation — not tariff-derived rules. These inputs are deliberately outside the tariff-traceability contract: the numbers — the rates the user speculates — live only in the call input, never in ports.json, any rate table, or any extraction reference. No data file, engine rate table, or extraction-reference change carries OPS speculation; the engine prices exactly what the user enters, nothing more. ### 4.2.5 Godsavgift: The Sjöfartsverket Cargo-Based Fairway Due (v0.2.61)

The Sjöfartsverket godsavgift (2026 price list p.5, effective 2026-01-01; Föreskrift 2025:6 om farledsavgift) is a national cargo-based charge in the fairway-dues family, levied at every Swedish port — Gothenburg and Helsingborg each carry their own transcription with their own citations (port-silo principle; the rule ids sjofartsverket_godsavgift and sfv_godsavgift never share a file). Rates: 3.36 kr/tonne high-value cargo, 1.67 kr/tonne low-value cargo. The charge stacks with Helsingborg's municipal Port-of-Helsingborg cargo due — separate charges, both fire on the same call. Hamburg levies no godsavgift and renders no cargo-tonnage input group.

Traffic-type basis: international traffic is charged on loaded and discharged cargo (both directions), domestic traffic on loaded only. The call model cannot distinguish traffic type, so the international basis is the default and the assumption is disclosed in the line's basis string ("international basis assumed"); the domestic variant is recorded as a deferred finding. Transit cargo is exempt per the price list; the call model cannot represent transit cargo, and that limitation is stated in the basis string — never silently assumed.

Input surface: three shared, cargo-technical call fields — cargo_weight_per_20ft (default 14 t), cargo_weight_per_40ft (default 24 t), cargo_low_value_share (default 0%). The weights are suggested planning parameters, not tariff data (the OECD 12–18 t/TEU band notice renders on both inputs; user-adjustable). The share default's basis: 100% high-value for container vessels per the SJÖFS commodity-code annex; the input exists for mixed and non-container calls. The fields are shared and currency-neutral — kWh-like persistence semantics: they survive port switches until page refresh or the per-workspace reset, and they are deliberately absent from every port's reset_fields.

Derivation: cargo tonnes = (20ft boxes loaded + discharged) × avg-20 weight + (40ft boxes loaded + discharged) × avg-40 weight, rounded to the nearest whole tonne (SJÖFS 16 §). Godsavgift = tonnes × (high share × 3.36 + low share × 1.67); the blended effective rate renders derived with its derivation shown (e.g. 25% low → 2.9375 kr/t effective). Zero or blank container counts render no line at all — no zero-tonne line, no division artifacts. The line's derived effective per-GT follows the v0.2.30 convention ("derived, not a published rate").

### 4.2.6 Call-Frequency What-If Panel: Speculation Outside the Call Model (v0.2.63)

The frequency rabatt and its equivalents are presentation-layer what-if territory, not call-model inputs: the call model prices one call, and a month of calls is a scenario the user speculates about. The panel is a per-port, workspace-side, collapsed-by-default disclosure ("Call frequency what-if"), in the OPS speculation styling family, rendered in every port's workspace below the OPS block; the comparison view carries nothing of it (a per-port percentage row is a possible future pass, deliberately not added).

The output for a representative call N of the calendar month: the payable percentage resolved from the port file's own frequency_discount bands (data, never a code copy), the waived components itemized (vessel fee and readiness fee, with per-line waived shares), the continuing cargo-based lines (godsavgift continues at every call — the sources' own rule, prislista 2026 p.4), the per-call total for that call, the delta versus the current single-call model, and the percentage against the current call total (currency-neutral, no conversion disclosure; the kr delta follows local-currency rendering). Every figure derives from the engine's own result lines — the panel never recomputes an engine rule and never re-prices the call. ### 4.2.7 Comparison Legibility: Discounts Received, OPS Stage Placement, and the Per-GT OPS Disclosure (v0.2.64)

Three comparison-surface presentation contracts, zero figure drift (the rendered Grand Total and stage-subtotal strings are byte-identical to the pre-v0.2.64 baseline, pinned; no engine, data, or call-model change).

**Discounts received.** The comparison carries a "Discounts received" line per port (desktop row and mobile card line), rendered before the Grand Total, clearly labeled as included in it (never additive). The line's content is the sum of the tariff-derived negative adjustments firing at the current call, and only those: the amounts are the engine's own derivation adjustment deltas (spec v0.2.42) — rule-level discounts (conditioned, additive stacks, per-GT rebates), component adjustments (Tier, ESI air/noise, Quantum, the HPA OPS rebate), and the per-biller frequency-discount line — each itemized with its amount and the engine's own source-reference citation. Speculation inputs are structurally excluded, never filtered: OPS amounts carry no fee derivation and the frequency what-if panel (section 4.2.6) never feeds the engine, so no speculation value can enter the line at any input state. The sum renders in local currency through the existing conversion disclosure machinery; the percentage is currency-neutral — the sum against the port's gross (pre-discount) charges, where gross = tariff-derived net charges (the Grand Total minus the user-specified OPS block when entered) plus the discount sum. The default single call renders the honest zero meaningfully (the audited inventory: no discount fires at the default call at any port — GOT's second-call 50% needs calls_this_month ≥ 2, the environmental discounts need entries the worst-case defaults leave blank, HAM's quantum needs prior-year GT, the Tier adjustment is a surcharge at the estimated Tier II); a port with no firing discount at the current call renders the explicit "no discounts at this call" state, never a silent absence.

**OPS stage placement.** The user-specified OPS block renders inside the "At the berth" stage block on both comparison surfaces — the desktop row within the at-berth stage fragment, the mobile card line within the at-berth stage block — positioned before the Grand Total and labeled "included in the Grand Total". The placement is comparison-surface presentation only: the workspace inputs keep their speculation notices, the block keeps its separated warning styling and its per-port isolation (v0.2.62), blank still renders nothing, and no absence wording renders for ports without values.

**The per-GT OPS disclosure.** Audit verdict (v0.2.64): no published tariff prices container-terminal OPS per GT — the Gothenburg Port Tariff 2026 carries exactly one OPS charge, the flat 7,000 SEK connection fee at the Energy Port tanker jetties 519/520/521 (tanker-gated, already encoded), and no Swedish port's tariff publishes any other container-terminal OPS charge. The speculation-input treatment is therefore the honest one, and where a per-GT OPS charge is entered the derived SEK/GT metric carries the disclosure that the user-specified per-GT OPS figure uses the same GT basis as the port dues and flows into the derived metric; the workspace per-GT input's helper text carries the same disclosure with the no-published-rate statement.

### 4.2.3 Scenario-Adjustment Layer: Contract Rates and Manual Overrides

**Status: deferred — design contract only, not implemented in v1.** This section records the intended design so future implementation follows it; no engine, data, or UI surface implements it as of v0.2.32, and no test enforces it (the spec-health review of v0.2.32 marks it explicitly rather than leaving the gap implicit). The estimated-parameter inputs (handling rate, towage amount, tug count, gangway class and count) provide the v1 subset of this layer: user-overridable rates, flagged as estimates rather than contract overlays.

The published tariff is the default baseline and remains untouchable in normal use. The scenario-adjustment layer lets the user overlay adjustments that reflect data only they hold, without ever editing the sourced port files.

Structure. An adjustment set is a per-session overlay consisting of adjustment rules, each specifying:

- Target: a fee family, a biller, or a fee family within a biller (e.g. port dues at the port authority; terminal handling at APMT; OPS energy).
- Operation: percentage (plus or minus) or absolute replacement of the rate. Absolute replacement covers negotiated fixed rates ("instead of 412 we pay 380 per unit") and is not limited to discounts; upward adjustments (rate increases, percentage or absolute) are equally supported for adverse-scenario modelling.
- Scope option: whole fee, or the rate component within a progressive band structure where meaningful.

Primary use case — contract rates. Shipping lines rarely pay published tariff rates; they negotiate discounts on port dues, per-unit lift costs, shifting, and other charges. A user with private contract knowledge enters their negotiated terms as an overlay (e.g. port dues minus 20 percent, terminal handling at 380 per unit instead of 412) and the app computes what their call actually costs, while the tariff baseline remains one click away for comparison. This directly operationalizes the contract-vs-published caveat recorded at v0.2.4: instead of a warning that real rates may differ, the tool lets the user supply them. Contract terms are private data; the overlay lives only in the user's session or local storage, never in the shared, sourced dataset.

Second use case — adverse-scenario and sensitivity modelling. The same mechanism, run in the positive direction, answers the opposite question: if negotiations fail and the published rates stand, or if the port raises tariffs, or electricity prices spike, what does the call cost then? Overlays such as port dues plus 10 percent, handling at 450 per unit, or shore power at a higher reference price let the user stress-test a call or a port comparison against plausible bad outcomes. Because adjustments toggle individually, a user can compare baseline, contract, and adverse scenarios on the same call inputs side by side.

Display and integrity rules:

- Adjusted lines are visibly marked and itemized as their own entries (baseline X, contract adjustment minus Y percent, effective Z), so a scenario can never be mistaken for the verified tariff result.
- Every view distinguishes baseline mode from adjusted mode, and the comparison views state which basis they use.
- Adjustments can be toggled on and off individually, and the default state on load is always the pure baseline.
- Order of operations relative to tariff-native discounts: contract adjustments apply after the tariff's own discount logic (ESI, frequency, volume), since negotiated terms are typically expressed off the net or gross rate as specified in the contract; the overlay rule carries an applies_to field (net / gross) to record which.

Not in scope for v1: persistence of named scenario profiles across sessions beyond local storage, and any sharing or synchronization of contract data — deliberate, since contract rates are commercially sensitive.

Per-port regulatory applicability. The AFIR/FuelEU obligations do not apply uniformly: they attach to TEN-T core and comprehensive maritime ports, and not all ports or terminals fall within that network — smaller ports are outside the mandate. Applicability is therefore a per-port data attribute, not a global constant. **Status: deferred — design contract only.** No port file carries the regulatory block as of v0.2.32 (no 2026 tariff in the initial set is subject to the mandate, which begins 2030); the design stands for the first TEN-T port encoding that needs it.

- Each port file carries a regulatory block: ten_t_status (core / comprehensive / not_in_network, with source reference to the TEN-T network designation), plus the date from which the OPS mandate applies at that port's berths.
- The UI reacts to the selected port and terminal: at a mandated port, a call dated on or after the mandate date with a vessel above 5,000 GT defaults OPS on and shows the regulatory notice; at a non-TEN-T port, OPS remains a plain optional input with no mandate notice, and the energy-at-berth segment simply reflects whatever the user chooses.
- Where a port is in the network but a specific terminal lacks OPS infrastructure, the terminal-level override is recorded the same way (with source), and the UI shows a distinct notice: mandate applies but infrastructure unavailable at this terminal — a compliance risk flag rather than a cost line.

Exact applicability criteria (AFIR Regulation (EU) 2023/1804, Article 9; corroborated by T&E's AFIR explainer and secondary regulatory guides). Being a TEN-T core or comprehensive maritime port is necessary but not sufficient. The port must additionally exceed ship-category call-frequency thresholds, counted as annual averages over the preceding three years, counting only calls by ships above 5,000 GT:

- More than 100 port calls per year by containerships, OR
- more than 40 port calls per year by ro-ro passenger ships and high-speed passenger craft, OR
- more than 25 port calls per year by other passenger ships (cruise).

Where these thresholds are exceeded, the member state must ensure OPS capacity covering at least 90 percent of port calls by the relevant categories. For the ship-side duty, FuelEU Maritime Article 6 adds operational conditions: the vessel must be a container or passenger ship above 5,000 GT, moored for more than two hours, at a port of call under AFIR Article 9 — with defined exceptions (stays under two hours, zero-emission technology meeting Annex III, unscheduled safety calls, documented infrastructure unavailability, ship-shore incompatibility, emergencies, maintenance).

Consequence for the model: the port regulatory block carries the threshold evidence — ten_t_status, the three-year average call counts by category, and the resulting mandate determination, each with a source reference and a verified_on date. The UI's mandate notice is then fully explainable: it can show not just "AFIR applies" but why (TEN-T comprehensive; 142 containership calls per year average 2023–2025, above the 100 threshold). Ports below the thresholds show OPS as optional with a neutral note that the port falls outside the AFIR mandate thresholds. The vessel-side conditions (above 5,000 GT, container or passenger, moored over two hours) are evaluated by the engine from the call inputs, so the notice also reacts correctly to vessel presets.

Phasing beyond 2030. The ship-side OPS duty reaches further over time:

- From 1 January 2030: container and passenger ships above 5,000 GT at ports covered by AFIR Article 9 (as above).
- From 1 January 2035: the duty extends to ports not covered by AFIR Article 9 but equipped with OPS.
- Between 2030 and 2035, member states may impose OPS usage earlier at non-covered equipped ports, with notification to the Commission a year in advance; they may also extend the requirement to ships at anchorage.
- The AFIR infrastructure obligation (90 percent coverage) applies from 31 December 2029.

The engine therefore evaluates the mandate in three tiers by call date and port attributes: AFIR-covered port (2030), equipped non-covered port (2035), unequipped non-covered port (never — OPS remains optional). The member-state options (early imposition, anchorage) are recorded as port-level flags where known, defaulting to off with a data-quality note. Out of scope for the cost model: FuelEU flexibility mechanisms — pooling, banking, and borrowing of compliance balance — affect fleet-level GHG-intensity compliance economics, not per-call port costs, and are deliberately excluded.

This keeps the reaction deterministic and traceable: the behaviour follows from sourced facts in the port file, never from hard-coded port names in the application, preserving the ports-are-data principle. The TEN-T designation of each port in the initial set is to be verified and recorded during port encoding (open item).

### 4.3 Data and Presentation Layers

The data layer and the presentation layer are strictly decoupled.

Data layer: a rich, normalized model of cost items — every individual charge as a distinct record carrying its biller, fee family, formula, conditions, currency, and source reference. The model is deliberately over-specified relative to any single UI need, so that views, upgrades, and tariff changes never require data restructuring. Physically, in version 1, this model is stored as versioned structured files (YAML for authoring, JSON as the interchange format the application consumes), reviewable on GitHub. A database may be introduced later without redesign.

Presentation layer: the GUI derives all views from the data layer's output contract. The default view is a simple overview (port totals and top-level groupings); any grouping — by biller, fee family, or port — can be collapsed, expanded, or drilled into on request. Detail (individual clauses, tariff documents, calculation traces) is retrievable on demand rather than shown by default.

Line-labeling rule. In any results rendering, the fee family is the grouping and the rule name is the line: when more than one rule of a family is active on a call, each line is labeled by its distinct rule name (e.g. Solid Waste Dues and Sludge Waste Dues), never collapsed to the family label alone. This holds for all families and all views, including the comparison view's drill-down. Whether waste should further split into separate fee families (waste_solid / waste_sludge) is deferred until a second port is extracted, since family taxonomy is a cross-port decision.

The exact interaction design of the GUI is deferred. What is normative now is that the data model must be sophisticated enough that no future presentation choice is constrained by it.

### 4.3.1 Multi-Port Navigation and the Comparison View

When more than one port is loaded, the UI is organized as separate per-port pages rather than one accumulating screen. A persistent port selector (navigation tab bar or equivalent) moves between per-port workspaces; each workspace contains the full form-and-results experience for that port, using that port's fee families, form fields, and data. Per-port separation is required: fee families and inputs differ between ports, and a single combined screen would become unusable as ports are added. Since v0.2.59 each port's rendered input surface is itself data-authored: the port file carries an `input_profile` section (which field-level inputs render inside the shared groups, which section blocks render, and each section's operator list), so a new port's form ships with its authoring rather than a JSX edit; the workspace renders the profile, and an unregistered profile fails loudly at lookup, never a silently empty form. Since v0.2.60 the same `input_profile` section also carries the port's `reset_fields` — the call fields that are per-port state rather than shared (exactly the fields the port's own workspace renders or prices port-specifically; GOT 17, HAM 20, HEL 21, the union equal to the retired hand-kept array) — so a new port's persistence scope ships with its authoring too. **Per-port persisted call state (v0.2.60, repairing the v0.2.20 wipe-on-switch as a defect).** Port-specific call inputs are per-port state, never wiped on a port switch: a value entered at a port survives switches (until page refresh) and renders only in that port's workspace and comparison column. The App splits every workspace edit by the reset_fields union — per-port fields route to the editing port's own state, every other field is shared and carries across ports; the comparison consumes each port's own entries through the same v0.2.53-ordered merge (per-port defaults under the stripped shared call under the port's own entries), and an explicitly entered shared value still wins over per-port defaults. Currency safety follows from the isolation itself: an SEK value never renders in a EUR input box because each port's workspace reads its own state — not from wiping. Shared currency-neutral fields (OPS kWh consumption, and any future cargo fields) stay shared by not being declared in any reset_fields list. Each workspace carries an explicit "Reset <port> inputs to defaults" control that clears that port's own fields alone; shared inputs and other ports' entries survive it. The v0.2.20 wipe-on-switch behavior (port-specific inputs reset to defaults on switch) is superseded: it destroyed entered per-port values — most acutely the currency-specific OPS speculation, which could not be entered and compared at all.

**The comparison view.** A distinct comparison screen (not a mode of a per-port page) answers the question "what would this same vessel, this same call, cost across these ports?" Behavior:

- The user selects the ports to compare (any subset of loaded ports) and enters the vessel and call parameters once. Parameters map to each port's rules; where a port has no equivalent input (e.g. a fee the port does not charge), that port shows no line for it rather than an error. Since v0.2.59 the fresh-load default is an explicit bounded selection — the first four loaded ports (all three today, identical DOM) — never an automatic all-ports rendering; the selection list remains the explicit subset control as ports are added.
- The comparison renders one column per selected port, with rows by cost segment (vessel call / energy at berth / yard & storage) and, drillable, by fee family. Segment subtotals and the grand total per port are always visible; the cheapest/most expensive port per row is visually marked. Since v0.2.59 the columns (and their mobile cards) render cheapest-first by Grand Total on the converted comparison basis — the same single ranking rule behind the cheapest/most-expensive markers (rankOrderByConvertedBasis); the per-GT row ranks identically by construction (same Grand Total divided by the same call GT), so it carries no separate rule; unpriced (errored) ports render after the priced ones. Since v0.2.60 every port column keeps a 140 px readability floor (.comparison-table th/td:not(:first-child), a fixed px value rather than a spacing token — the scale is for paddings/gaps, a column floor is a readability constraint), so as the selected-port count grows the table degrades by horizontal scroll inside its container, never by squeezing columns to unreadable widths; the label column keeps the v0.2.43 fit contract (wraps, bounded max-width, no min-width, so no forced gap can appear before the port columns); the mobile card layout below the 600 px stacking breakpoint does not render the table and is untouched by the floor.
- Comparability rules from 4.2 apply: rows group by function (fee family), never by biller name, so ports that charge differently for the same function still line up. Where a function is genuinely absent at a port, the row shows an explicit "not levied at this port" (the v0.2.52 wording, superseding the earlier "not charged") rather than being hidden, so an absence of cost is never mistaken for missing data.
- The comparison uses reference tariff rates only (list prices); contract rates and manual overrides from the scenario-adjustment layer may be applied per port, clearly marked, but the default comparison is list-price.
- Data quality is carried through: lines derived from unpublished or estimated rates carry the same flags as in per-port views, and a comparison including such lines is marked accordingly.

**Line labeling in the comparison.** The line-labeling rule (4.3) applies unchanged: the fee family is the row grouping (economic function, never biller name, so ports that carve the same function up differently still line up), and each line within a row is labeled by its distinct rule name with the biller shown per line (e.g. Pilotage Dues (Lotsabgaben) · GDWS). Lines derived from estimated parameters carry the estimate marker, exactly as in per-port views.

**Local currency and cross-currency comparability.** Every amount, subtotal, and total in the comparison renders in the tariff's local currency (EUR Hamburg, SEK Gothenburg); the engine performs no conversion anywhere. Cross-currency comparability follows the Section 6 contract (v0.2.31): cross-port aggregate rows render native-primary with a converted-secondary figure, ranking uses the converted comparison basis (SEK) while display keeps native-primary, and the kr-per-EUR rate (a versioned data default, user-editable, with recorded source and as-of date) renders beside every converted figure. The earlier optional end-of-comparison conversion step was removed in v0.2.31; rankings never compare raw amounts across currencies.

The comparison view reads the same canonical data and engine as per-port pages — it is a presentation over multiple single-port computations, not a separate calculation path.

### 4.4 Fee Rule Elements

Each fee rule in a port file carries five elements:

1. Base unit — what the fee is charged per: GT, move, commenced day, tug-hour, m³ water, kWh, flat.
2. Rate structure — one of:
   - flat: single rate per unit;
   - banded: the applicable rate per unit depends on which band the vessel's GT (or other key) falls into — e.g. Gothenburg port dues;
   - progressive: bands applied cumulatively to the portion within each band;
   - per_commenced_day and similar time-based forms.
3. Conditions — predicates on vessel or call parameters: traffic category, LOA thresholds, emission class or ESI score, OPS usage, laytime duration. A rule with unmet conditions does not apply.
4. Adjustments — percentage discounts or surcharges that may stack (ESI ladders, green-port surcharges, environmental indexing).
5. Currency and validity — mandatory currency, effective-from date, and source reference (document filename, page, clause).

#### 4.4.1 Adjustment Stacking Semantics

When multiple adjustments apply to a single fee, the combination method is declared per tariff clause where the tariff itself legislates the method (recommended default). Where a tariff is silent, adjustments apply multiplicatively in a defined order: surcharges first, then discounts, each applied to the running result. This is subject to iteration as real tariffs are encoded and edge cases emerge.

#### 4.4.2 Missing-Parameter Fallback

If a rule references a parameter the user did not supply (for example, an ESI-dependent discount with no ESI score entered), the tool assumes the least favourable value (no discount applied) and displays a visible notice on the result line, so the user is aware that a potentially applicable benefit was not computed.

**Default-call contract (v0.2.28).** The default call is the worst-case published-rate call: every port at its published ceiling, max-vs-max. No environmental discount, ESI score, CSI class, fossil-free-fuel share, or equivalent lever may reduce any figure unless the user explicitly enters it — defaults are never discounting. A blank input means "not entered" and is never interpreted as a numeric score (a zero ESI is a legitimate score of zero only when the user types it; the initial form value is blank, and the input's helper text states this). The Sjöfartsverket environmental class defaults to E (not registered), the least favourable published rate; the Clean Shipping Index class defaults to blank (no port discount); the Hamburg quantum prior-year GT defaults to 0 and the OPS toggle to off; all waste-reduction toggles default off. The shared default form state lives in core (`core/src/defaults.ts`) so the core test suite pins the actual initial form values, and a test asserts that a default call yields zero environmental discount at every port — the default result equals the explicitly no-discount computation — while an explicitly entered ESI score still discounts, guarding against a dead input. (Amended v0.2.59: the shared worst-case core stays in code, but every port-specific default value is now data-authored — each port file carries a `default_call` section, registered through the port-data registry and overlaid on the shared core, so a new port ships its defaults with its authoring rather than an engine edit; YAML null normalizes to undefined per this section's blank contract; the lookup fails loudly — an unregistered port throws at defaultCall, never a silently empty default; and the v0.2.53 comparison merge contract is preserved exactly: explicit shared-call values still win over per-port defaults.)

**Storage rule (v0.2.33).** Days within free time charge zero, and the seeded storage days (export 5, import 3) sit within every port's free allowance, so the default call at every port yields zero storage lines and zero yard-surcharge lines — a guarantee pinned by tests, not an emergent property. The engine's `banded_by_time` semantics are ladder semantics: each storage day charges exactly once, at the first band whose [min_days, max_days] interval covers that day number; a day count below a band minimum (including zero) charges zero, never the full count at the band rate. No charge may fire from a seeded unit count: special-cargo unit counts (reefer, out-of-gauge, dangerous goods, overdue units) default blank — "not entered", computing zero — because a seeded count manufactures charges no user entered; a user-entered zero is a value and also computes zero, but only by the user's own attestation. Per-unit-per-day charges (yard surcharges) multiply days × rate × units, and a penalty rate (the overdue dangerous-goods penalty) is additionally gated behind its own explicit input.

**Operational-assumption rule for tug defaults (v0.2.33).** Where a port has no published towage tariff, the estimated-towage lever applies per-port LOA-class tug defaults, encoded as data (spec 3.3), applied only when the user supplied no tug count, and raised as a named `assumed_parameter` flag on the line: "tug requirement not entered; port default of N tugs applied; enter the actual requirement to override" — the flag names the assumed parameter specifically (badge honesty, v0.2.29) and never contaminates the estimated-parameters subtotal's meaning (the towage line itself remains `estimated_parameter`-flagged because the rate is an estimate). A user-entered zero tug count is a value, not a missing entry: it computes zero and suppresses the assumption flag. The per-port defaults derive from defensible operational reasoning (recorded with citations in the port's extraction reference); as of v0.2.33: Gothenburg and Helsingborg — LOA < 150 m: 0; 150–250 m: 1; > 250 m: 2 (Swedish West Coast/Kattegat fairway regime; open-harbour container terminals without a compulsory-tug clause in either port tariff); Hamburg — per-call estimate, no LOA-class encoding (deep-sea Elbe escort, 3 tugs × ~5,000 EUR market range as the declared per-call default).

**Comparison philosophy (v0.2.48; selection clause amended v0.2.59).** A comparison prices one identical call at every selected port (three ports today; the fresh-load default is bounded and the selection control bounds the set) — same vessel, same lay time, same container moves, same environmental classes — so the port is the only variable. Per-port call-size variation is deliberately excluded from the comparison: the tool does not model that a feeder would not call at Hamburg or that a Triple-E would not call at Helsingborg; the user prices the call they specify, everywhere. The comparison context strip (v0.2.47) states the call's assumptions once above the table — vessel, GT, TEU capacity, moves, lay time, classes, with seeded-profile and default annotations per the honesty rules — so every figure in the table reads as "this call, priced at three ports". The per-port views remain fully editable: changing any input there prices the changed call everywhere it is shown. Voyage-leg attributes are held constant across ports exactly like lay time and moves (v0.2.50): the arrival origin — the previous port of call's region, European or outside Europe — is one shared leg selector on the call, and a real rotation's sequence of legs (Asia → Hamburg → Gothenburg) is deliberately out of scope, priced by flipping the selector; a per-port origin override is explicitly deferred as a considered future option ("rotation mode"), not implemented.

**Raw versus negotiated (v0.2.49).** The tool's outputs are published-tariff ceilings. Carriers with negotiating power typically realize lower effective costs than the published rates; a raw-tariff figure standing above a negotiated benchmark is the expected, defensible relationship, not a defect indication.

**Helsingborg ISSC / no-ISSC state contract (v0.2.53).** The port security fee's ISSC condition is a three-state input, and every state is honest: a valid ISSC prices the single rate (78.00 SEK per unit) with no flag; an explicitly attested absence (no valid ISSC) prices the doubled fee (156.00 SEK per unit, tariff p.6) with the SOLAS XI-2/ISPS consequence sentence on the line — the user stated the absence, nothing was assumed, so it is an information flag, never a fallback; a blank (not entered) status resolves to the least favourable value per 4.4.2 — the doubled fee — with a visible fallback flag stating that a valid International Ship Security Certificate halves the fee back to the single rate, never silently. Exactly one security line fires per call; the valid and doubled rules are mutually exclusive. ISSC gating exists only at Helsingborg — no Gothenburg or Hamburg rule references it.
**Gothenburg waste dues (v0.2.50).** Gothenburg's ship-generated waste dues are a compulsory statutory charge: the per-GT base applies to every calling vessel in accordance with Swedish legislation, and only a Transport Agency exemption (tariff §12) relieves it. The split dimension is the arrival origin — the previous port of call's region, never the flag: sludge 0.21 SEK/GT (arrival from a European port, up to 11 m³ included) / 0.31 SEK/GT (arrival from outside Europe), solid waste 0.13 / 0.24 SEK/GT by the same origin split; volume beyond the 11 m³ included sludge volume is charged at 2,400 SEK/m³ through an optional excess input, and the per-GT base computes on every call regardless. A vessel holding EU Implementing Regulation 2022/91 certification takes −0.05 SEK/GT off the solid-waste line only, through an explicit attestation input defaulting to false (never assumed). The §12 Transport Agency exemption is recorded as an explicit documented deferral: the per-vessel regulatory grant is rare and no input silently suppresses the compulsory lines. The scrubber-waste line stays honest: 800 SEK administration fee only, actual disposal cost excluded and labeled as such. The former flag-state gating of these four rules was a defect and is retired: flag_state now drives nothing in any port's data (the four Gothenburg waste rules were the only flag-gated rules anywhere), and the engine raises a visible warning if a data rule ever re-carries a flag_state condition.

**Terminal scope (v0.2.49).** A Hamburg call is priced against a named terminal operator. HHLA ship's-dues and terminal items apply only to HHLA calls (the reference operator and default); EUROGATE items (berthing charge 2.1.1/2.1.2, waterside handling 5.1.1, security 13.1, the 1.5% social fund) apply only to Eurogate calls; the two sets can never co-fire in one call. Port-wide charges (HPA port fee and demurrage, GDWS pilotage, BUKEA waste, towage) are operator-neutral and fire for every Hamburg call. An absent or unrecognized terminal-operator value falls back to HHLA with a visible fallback flag, never silently. The comparison context strip states the priced operator once, with the same honesty rules as every other default.

**Classification rule (v0.2.29, amended v0.2.44).** Classifications differ from discounts in one way: every vessel objectively has a NOx Tier, so the tariff has no "no Tier" state. When the Hamburg engine tier is not explicitly entered and a build year is entered, the NOx tier is inferred from the build year per MARPOL Annex VI Regulation 13 construction dates (build year 2000 or later → Tier I; 2011 or later → Tier II; 2016 or later → Tier III — ships constructed on or after 1 January 2016, Tier III being the in-NECA standard the construction date determines; pre-2000 → Tier 0). The inferred tier applies to the environmental component exactly as an entered tier would, and a named assumed-parameter flag is raised ("engine tier inferred from build year — verify against IAPP certificate"), rendered adjacent to the figure it affected per the v0.2.42 derivation-transparency contract. Blank build year keeps the v0.2.28 worst-case Tier 0 default with its existing flag — the worst-case contract stands for truly unknown vessels. Explicit tier entry always wins over inference and clears the inferred flag. The v0.2.29 rule that the build-year heuristic is never invoked silently is amended for this one field: the inference is now the default behavior when a build year is present, always flagged, never silent; the superseded explicit user action is removed from the UI and the `infer_engine_tier_from_build_year` state flag is repurposed as the inference contract's wiring state (false; an explicit tier entry clears it). The vessel library carries an optional `engine_tier` field so a library-selected vessel with a certified tier computes without the flag. Badge honesty: any flag generated by an assumed vessel parameter must name that parameter specifically; a fully-specified charge must never render a generic "estimated" badge. In particular the Hamburg Port Fee must not read as an estimated charge when only its Tier is assumed — the tariff rates, bands, cap, and minimum are verified data; the line shows a "NOx Tier assumed" badge, and the assumed-parameter flag never contaminates the estimated-parameters subtotal.

**Environmental-input guidance (v0.2.29).** Each environmental input (NOx Tier, ESI score, ESI noise, CSI class, fossil-free share, Quantum, OPS) carries a help affordance consistent with the form's helper-text and disclosure patterns. Expanded, it shows: what the certificate or score is and who issues it; the decision rule in user terms (Tier = most polluting engine per the IAPP supplement; without proof, Tier 0 applies); the port's current threshold bands from the port file, with source references; and the computed money consequence of entering each value on this call ("entering Tier II instead of the Tier 0 default changes this call by −X"), rendered before any value is entered. The guidance panel is purely informative: no auto-fill, no pre-selection, no persistence; money-consequence deltas state they are per this call and per this port. The v0.2.29 "purely informative" rule is amended for exactly one input (v0.2.44): the build year, which drives the Hamburg tier inference per the classification rule above; every other environmental input remains guidance-only — ESI score, ESI noise, CSI class, fossil-free share, Quantum, and the OPS prerequisites never mutate calculation state from the guidance affordance. External issuing-body links are verified live before shipping. A compact per-port overview lists which levers apply where. WCAG 2.2 AA remains the standing floor for the affordance (keyboard operable, aria-expanded/aria-controls).

#### 4.4.3 Data Validation

The application validates port files on load. If it encounters an unknown fee family, it does not silently proceed; it prompts the user to interpret or classify the item, accompanied by an explicit warning that calculation quality may be severely impacted. Banded structures with gaps or overlaps between bands are rejected at load time.

### 4.6 Worked Contrast: Banded vs Progressive vs Flat

- Gothenburg container vessels (progressive): the tariff explicitly states "progressive banding" — the first 20,000 GT charged at the 0 to 20,000 GT band rate, the next 20,000 GT at the 20,001 to 40,000 GT band rate, and so on. Each GT portion is charged at its own band rate, exactly like Hamburg.
- Gothenburg tankers (banded): the tariff states "Dues are calculated based on GT bands, and for the vessel's total GT" — one rate applies to the entire GT based on which band the vessel falls into. This demonstrates that a single port may use different rate structures for different vessel types.
- Helsingborg (flat): a single flat SEK/GT rate regardless of vessel size — same engine, rate.type set to flat instead of banded or progressive.
- Hamburg container vessels (progressive): GT split pro-rata across three bands, each portion at its own rate. Formerly split by shipping area (intra-European vs deep-sea) with three components (GT, handling/quantity, environmental) as of the 2020 tariff; reformed in 2024 to the current progressive structure. The 2026 tariff continues this progressive structure.

Both Gothenburg and Hamburg use progressive banding for container vessels, but with different band structures, rates, currencies, and additional components. This confirms that the progressive rate type is essential and common, not an edge case.

### 4.7 Tariff Versioning

Prior-year tariff versions are kept loaded alongside the current version, so users can compare historical or future-dated calls. The call date selects which tariff version applies. Critically, the rule engine must handle not only rate changes between versions but structural form changes — for example, Hamburg's port dues shifting from a traffic-category split (intra-European vs deep-sea, sub-50k GT threshold) to a banded GT structure. The version selector determines which set of rules is evaluated; the engine itself remains generic and does not hard-code any particular structure for any year.

### 4.8 Presentation Principles (v0.2.25)

The application reads as a professional financial analysis tool: dense, calm, data-forward. The numbers are the interface; every aesthetic decision is subordinate to legibility of figures, traceability of provenance, and comparability at a glance. Where decoration and clarity compete, clarity wins.

**Design system.** Conventions borrowed from IBM Carbon, implemented natively (no UI dependency added): a 4 px spacing scale (all padding, margins, and gaps from 4/8/12/16/24/32/48); a five-step type scale defined once (caption 12, body 14, subtitle 16, headline 20, display 28); one 8 px grid for all components; defined hover, focus-visible, active, and disabled states for every interactive element, with clearly visible focus indicators (WCAG 2.4.7). Every figure renders in a monospaced/tabular-numeral face so columns of amounts align.

**Theme architecture.** All colors are semantic CSS custom properties on the root element: surface, surface-raised, surface-sunken, border, border-strong, text-primary, text-secondary, text-disabled, accent, positive (discounts), warning (estimates), error (defects/not-encoded), plus tint variants for badge backgrounds. The dark theme is the default and defines the tokens; the light theme is a mapping over the same token names — one design, two palettes, not two designs. The toggle sits in the header, persists in localStorage, and defaults to dark when no preference exists; prefers-color-scheme: light is honored only when the user has never toggled. Color carries meaning, not decoration: accent and status colors appear only on interactive elements and semantic markers; everything else is the neutral surface scale. Both themes must pass WCAG 2.2 AA contrast (4.5:1 normal text, 3:1 large text and UI components), verified programmatically for the defined token pairs. **Themed-color discipline (v0.2.51).** No results-area or comparison surface may hardcode a color — not in an MUI sx prop, not as a CSS literal outside the :root token blocks, not as a var() fallback literal: every background, border, and text color resolves through the theme tokens, so both modes render from one source. The v0.2.51 audit found the two violations of this rule (hardcoded #f5f5f5 summary blocks, invisible in dark mode since their introduction) plus ten #666 secondary-text siblings and one .btn literal; all are fixed and the discipline is pinned at the class level (jsdom cannot compute CSS custom-property cascades, so the class-level pins stand in for a computed-contrast check — stated limitation).

**Layout.** A single max-width reading column (~1440 px, centered). The header carries the title, theme toggle, and the persistent port selector; at wide viewports the form sits left and results right, stacked at narrow viewports, preserving the responsive segment rules of 4.2.1. The port selector, comparison view, and persistent total strip keep their existing behaviors; only presentation changes.

**Form.** Progressive disclosure: three staged cards — Vessel, Call, and Port-Specific Parameters — each with a clear header and summary. Vessel and Call are expanded by default; Port-Specific Parameters starts collapsed and expands on demand, rendering only the active port's fields. Inputs keep their existing semantics, defaults, and quality flags; vessel-library pre-fill keeps its estimate badges. Restyle only, never a semantic change.

**Results hierarchy.** Stephen Few's dashboard hierarchy and Tufte's data-ink discipline: the total is prominent (display type), segment subtotals secondary, line items tertiary — no more than two type sizes inside the results panel. Every figure right-aligned, thousands-separated, consistent decimal places per currency; the currency is stated once per column, not per cell. Decorative borders, dividers, and information-free icons are removed; whitespace and alignment do the grouping. The three-level provenance chain (amount → rate and basis → document/clause/page) keeps its expandable structure, restyled; estimate markers are small warning-tinted inline badges and contract-versus-published caveats neutral inline badges, so transparency survives density.

**Comparison view.** Styled as a formal financial statement: ports as columns, fee families as rows, aligned tabular figures, identical subtotal rules across ports. The estimate-separation rows (Grand Total / Estimated parameters subtotal / Total without estimates) render as clearly distinguished subtotal bands. "Not charged" and "not yet encoded" remain explicit cell values, visually distinct but present. Cross-currency aggregate rows render native-primary with a converted-secondary figure per the Section 6 contract (v0.2.31), with the rate and date beside every converted figure.

**Accessibility floor.** WCAG 2.2 AA is the standing acceptance floor for presentation changes: token contrast per above, keyboard navigability of every control including the theme toggle and all disclosure widgets, visible focus indicators, minimum 24 × 24 px targets (the design uses 32–48 px), and programmatic labels on every form field.

**Zero-line collapse (v0.2.27).** In the per-port results view, a zero-amount fee line collapses out of the main itemization when it carries no user-relevant information. A zero line is informative and must remain visible when: the line carries any quality flag (estimated parameter, contract-vs-published, least-favourable fallback); its rule declares a minimum-fee floor (a floor that did not bind is information about the charge); its rule is condition-gated — it fired on an explicit user selection, such as a class-variant rule chosen by the vessel's NT class, an ISSC-validity variant, or user-provided zero inputs on an always-relevant charge (e.g. pilotage hours = 0 with pilotage required); or its rule carries an estimated-parameter or contract-vs-published marker block. Otherwise — a plain per-unit or per-day rule, zero quantity, no flags, no floor, no conditions — the line collapses into one disclosure row per segment: "N charges not applicable to this call (0 kr / 0 €)", expandable to the full itemization with all presentational styling intact, keyboard-operable with aria-expanded/aria-controls consistent with the form disclosure cards. The comparison view applies the same collapse to true zero lines only, and only within cells, such that table symmetry is preserved: every fee family remains a row across all ports, and "not levied at this port" versus "not yet encoded" remain distinct visible values. The biller-breakdown and segment subtotals are unchanged by the collapse — they reflect computed figures, not line visibility. The classification is presentation-only: amounts, the engine output contract, and every checkpoint figure are untouched.

**Functional classification (v0.2.30).** Every fee rule in every port file carries exactly one function from the closed set: berth/terminal infrastructure; waterway/fairway access; readiness/safety capacity; cargo throughput levy; purchased service; waste/environmental. Assignments are derived from the tariff documents with the existing source-reference discipline and are pinned by tests as an exact rule-id map, so a future misclassification fails the suite rather than silently changing an aggregate figure. Expected composition, verified against the sources: at Gothenburg and Helsingborg, berth/terminal infrastructure = the municipal port dues; readiness/safety capacity = the Sjöfartsverket beredskapsavgift (readiness fee); waterway/fairway access = the Sjöfartsverket fartygsavgift (vessel fee). At Hamburg, berth/terminal infrastructure = the HPA port fee, plus the HHLA tonnage dues and the Hafenfonds surcharge placed by what their source documents actually fund (Quay Tariff §1.2: vessel fee "for the use of a quayside cargo handling facility"; §9.2.3: "Hafenfonds = port dues" surcharge on quay-tariff fees). The HHLA per-container security charge is a cargo throughput levy whose funded function is ISPS security; pilotage, gangway, and supervision are purchased services. The per-biller frequency-discount lines are classified to mirror the fees they adjust, so the aggregate nets correctly when a discount zeroes out the national fees. Godsavgift (the Sjöfartsverket national cargo fee) is classified waterway/fairway access since v0.2.61 (§4.2.5): the cargo-tonnage derivation fires it from the call's container counts and the shared planning weights; the earlier not-yet-encoded marking is closed.

**Vessel-access aggregate (v0.2.30).** "Vessel access charges" = the sum of this call's amounts for all rules classified berth/terminal infrastructure, waterway/fairway access, or readiness/safety capacity. The aggregate renders per port with an effective per-GT figure (sum ÷ vessel GT) as the derived comparability bridge. The rendering states the basis where it matters: the Swedish national fees are per-call by NT class, not per-GT — the effective-per-GT figure is the derived comparability bridge and is labeled as such, never presented as a published rate. When the Sjöfartsverket frequency discount applies, the discount line nets the national fees inside the aggregate (a 6-call month reduces the national fees to zero and the municipal dues carry their own frequency discount).

**Effective per-GT and derived-metric labeling (v0.2.30).** Every per-GT or per-call dues-type line renders its own effective per-GT (fee total ÷ vessel GT), labeled "effective rate for this call — derived, not a published rate." Where a minimum or cap materially binds (fee at the minimum; GT above the tranche cap; a per-call fee for a vessel far from its class boundary), the line carries a note naming the distorting factor (e.g. "fee at its 43.56 minimum", "per-call fee by NT class, not per GT"). Derived metrics never appear without the derived label; no effective rate is ever presented as a published tariff rate.

**Band disclosure (v0.2.30).** In the per-port results view, the expanded detail for every progressive or tranche per-GT rule renders one row per band actually charged — rates with components (Gothenburg's bands; Hamburg's GT + environmental €/GT per tranche), the GT quantity charged in that band, and the band's amount — then the sum, applied adjustments with amounts (Tier surcharge, discounts), cap/minimum notes, and the fee total. The rows are the engine's per-tranche per-component computation (the composite-tranche path emits per-component amounts); the UI renders them and never recomputes. A band that does not fire renders no row.

**Cross-country comparability note (v0.2.30).** Wherever the vessel-access aggregate renders cross-country (comparison view), it carries a comparability note derived from the functional classification — which functions each country's figure covers and which are funded elsewhere — never hard-coded prose. Hamburg's aggregate covers berth/terminal infrastructure only; the Swedish ports cover berth + national fairway + national readiness. The note states that functions not listed are funded outside the call's charges (e.g. nationally from taxation), so a per-GT comparison across the two systems is read with its basis stated.

Three charge-type lines render as prominent named rows, mapped per rule by rule id (never by fee family — the `vessel_fee` family collides across billers: Sjöfartsverket's is fairway dues, HHLA/Eurogate's is berth dues): **Fairway dues** — the Sjöfartsverket per-call national dues Fartygsavgift (per call by NT class × CSI class, prislista p.3) and Beredskapsavgift (per call by NT class, prislista p.4), plus since v0.2.61 the cargo-based Godsavgift (prislista p.5; §4.2.5), levied at Gothenburg and Helsingborg under the shared `sjofartsverket_`/`sfv_` prefixes, with their frequency-discount adjusters riding the same line; **Berth dues** — ship's dues for the berth/handling facility, GT × lay time, never cargo: HHLA tonnage dues (Quay Tariff §1.2; vessel-fee character per §9.1.1) and Eurogate berthing (Prices and Conditions 2.1.1–2.1.2) — the same economic animal, one line; **Cargo dues** — per unit/tonne of cargo handled: Helsingborg Port Dues Cargo (tariff p.6). Every rule lands in exactly one comparison line (charge-type line or remaining family row). The absence structure per port is stated honestly, never silently omitted: GOT levies no berth due and (for container calls) no per-unit cargo due — its Sjöfartsverket godsavgift rules exist in data but need a cargo-tonnage input the call does not carry (standing "not yet encoded" deferral); HAM levies no fairway due and no cargo due (its `cargo_fee`-family rules are container services under Quay Tariff §8, not cargo dues); HEL levies fairway dues but no lay-time berth charge (its port dues are per call/per unit, not per lay time). A charge type a port does not levy renders the explicit state "not levied at this port" in that port's column, as does a fee family a port does not carry.

**Comparison stages (v0.2.52).** Above the charge-type lines, the comparison view groups costs into three operational stages a call composes into, assigned per rule by economic function and operational stage over port-specific naming: **(a) To reach the berth** — port dues, fairway dues, pilotage, towage, waste, environmental surcharges, and the billers' statutory fund surcharges (hafenfonds, social fund); **(b) At the berth** — berth/tonnage dues and other lay-time-based charges, energy at berth; **(c) Quayside operations** — handling, security, cargo dues, storage, yard services. The stage grouping composes with the charge-type lines: charge-type lines nest under their stage (Fairway dues in stage a, Berth dues in stage b, Cargo dues in stage c), with the remaining fee-family rows grouped under the stage their function belongs to. The per-port views keep their existing Vessel Call / Energy at Berth / Yard & Storage segments — the stage grouping is a comparison-view presentation layer.

**Zero-line suppression (v0.2.52).** A comparison line (charge-type or fee-family) whose amount is zero at every compared port for the current inputs does not render in the comparison view. The suppression is display-only and conditional on computed values: rules still fire, derivations still compute, subtotals and the Grand Total are engine figures, and the engine is untouched. Any input change making a suppressed line nonzero renders it immediately (e.g. entering storage days beyond free time renders the storage line). The per-port view is not suppressed — its per-line visibility and the zero-collapse disclosure (v0.2.27) stand there unchanged. Note: the default comparison suppresses the all-zero lines (lay-up, hatch cover, gearbox handling, yard surcharge, gate hazardous, ancillary services under the default container call); the cargo line itself renders because Helsingborg's Port Dues Cargo prices unitized goods — for a zero-cargo call its suppression would be tariff-faithful, not a modeling gap (neither Swedish port levies a per-unit cargo due on a container call — Helsingborg's conventional-cargo exception does not reach unitized goods; Hamburg levies none). Visible lines plus suppressed zeros always equal the Grand Total.

**Default vessel (v0.2.48).** The default vessel is explicitly Maren Maersk (IMO 9632129): the default call is her profile — 194,849 GT, built 2014, 50 h lay time, 4,000 moves split 800/1,200/800/1,200, Tier II inferred from the build year with its flag — at every port. The choice is explicit (a named default in `core/src/defaults.ts` and `core/src/vessel_profiles.ts`), not a fresh-load equivalence: one named source of truth, pinned by tests, visible in the header and the comparison context strip with the same assumption annotations as an explicit selection. The default call remains the worst-case published-rate call in its discounting posture (v0.2.28: zero environmental discount at every port, still pinned); the default-vessel change is a deliberate contract change of the default call's scale, recorded in the changelog with before/after totals at all three ports. Worked-example checkpoints are unaffected: they enter their own inputs.

## 5. Per-Port Model and Output Contract

Each port file is a complete, self-contained costing model: an ordered list of fee rules plus port metadata (name, UN/LOCODE, currency, tariff documents, effective dates). Ports with fees others lack simply carry additional rules; absent fee families are reported as "not levied in this port".

### 5.1 Source Traceability

Every rate, every fee rule, and every computed result line must carry a full provenance chain that allows the user to independently verify accuracy against the original tariff document. This is not an optional feature; it is a core principle of the tool.

**At the data level**, every fee rule carries a mandatory source reference with the following fields:

| Field | Notes |
|---|---|
| document | filename of the tariff document stored in the port directory (e.g. got_port_tariff_2026.pdf) |
| document_url | the original public URL from which the document was retrieved |
| document_issued | the issue date stated on the document (e.g. 2025-10-09) |
| page | the page number in the document where the rate appears |
| clause | the clause, section, or tariff number (e.g. STC 4.1.2.4, tariff 217, price category 31 Step B) |
| verified_on | the date the rate was extracted and verified by the maintainer |
| verified_by | identifier of the person or session that extracted the rate |

A fee rule without a complete source reference is rejected at load time. No rate enters the system without being attributable to a specific location in a specific document on a specific date.

**At the output level**, every computed result line carries the same source reference forward, so the user sees not just what they are being charged but exactly where that charge is defined in the tariff. The source reference is visible in:

- The itemized breakdown table, per line item
- The drill-down detail view, alongside the calculation trace
- The CSV and JSON exports, as a structured field per row
- The REST API response, as a nested object per result line

**At the presentation level**, source references are shown by default in the drill-down view and available on demand in the overview. A user who sees "Port fee GT component: EUR 37,736.50" can expand that line to see "Source: Port_of_Hamburg-GTC_-_Pricelist_Maritime_Shipping_-_as_of_01.01.2026, page 6, tariff 31 Step B, verified 2026-09-20" and can follow the document URL to the original PDF.

**Document storage**: tariff PDFs are stored in each port directory under /docs and are the source of truth. The application does not parse them at runtime; it serves them for download or links to the original public URL so the user can open the exact document and navigate to the exact page and clause.

**Rate changes between versions**: when a rate changes between tariff versions, both the old and new source references are retained in the versioned port files, so a user comparing a 2024 call against a 2026 call can see not only the different rates but the different source documents and clauses that defined them.

**Source-link rendering (v0.2.26, revised v0.2.32)**: the YAML data files carry `document_url` as the repository-relative path of the stored source document — these paths are the file paths used for verification and stay as they are. At the data-conversion step (ports.json generation), every repository-relative `document_url` is rewritten to the absolute GitHub blob URL `https://github.com/Rekkike/VibesandTariffs/blob/main/<path>`, because `docs/sources/` is not part of the deployed static bundle and a relative hyperlink target would 404 on GitHub Pages. Absolute http(s) URLs pass through the conversion untouched. No source reference may point at an empty file: a source whose archive copy is absent from the repository carries an explicit `upstream_url` (the live publisher URL) in the YAML, and the converted registry marks it `document_not_archived` — the UI renders the provenance text with a link to the upstream publisher document and a "source not archived — upstream linked" marker. The zero-byte-placeholder mechanism of v0.2.26 (`document_pending`, "source document pending") is superseded and removed; it existed only while placeholder files awaited real PDFs and violated the no-empty-file rule. The core source-integrity test locks this layer: every fee rule's `document_url` path is either archived in the repository or explicitly not-archived with a live upstream URL, no zero-byte file may exist anywhere under `docs/sources` (terms-only documents included), and the path casing must match the repository exactly.

### 5.2 Shared Output Contract

**Shared output contract** (every port model must produce):

| Field | Notes |
|---|---|
| biller | charging entity: port authority, national/state authority, named terminal operator, independent service provider, or other costs (with free-text name) |
| fee_family | port_dues, fairway_dues, pilotage, towage, mooring, waste, security, ops, terminal_handling, storage, demurrage, berth_occupancy, anchorage, other |
| bundled_into | fee_id of the parent fee, if this cost item is subsumed within another charge; otherwise absent |
| description | human-readable line item |
| amount | in local currency, unrounded intermediate values |
| currency | ISO code |
| source_ref | full provenance object: document, document_url, document_issued, page, clause, verified_on, verified_by (see section 5.1) |
| validity | effective-from date |
| quality_flag | set when the fee family was unknown and user-interpreted, or when a required parameter was missing |

The comparison layer aggregates these per call: itemized breakdown per port, total per port in local currency, ranking, and per-line traceability. When a port's total is shown in another currency, conversion is applied uniformly at presentation (Section 6), so rankings never depend on the display currency.

### 5.3 Hamburg 2026 Port File (v1)

The Hamburg port file (`core/data/hamburg_2026.yaml`, port id `hamburg`, currency EUR, effective 2026) is encoded under the same schema as the Gothenburg pilot file, with four billers: **HPA (Hamburg Port Authority)** — port fee (GT and environmental components, cumulative-tranche over GT with adjustment stack: engine-Tier surcharge/discount, ESI air bands with euro caps, ESI noise, 225,000 GT cap, OPS rebate, quantum volume discount; minimum fee; 120 h coverage), demurrage beyond 120 h, and berth fees at HPA-operated berths (off by default; terminal berths do not trigger them); **GDWS (federal)** — Elbe pilotage dues and fees, GT-banded with a partial-transit segment percentage (default 100 % full Hamburg—Elbe buoy transit) and the published caps; and — the switchable terminal variant since v0.2.66 — **HHLA Container Terminals**: tonnage dues (first 24 h, then per commenced 12 h), gangway class (feeder/overseas) and supervision, per-container security fee, storage (free times, size-based daily rates, escalation), and the optional container-services set (reception/delivery, extra movement, admin, VGM, reefer connect/energy/check, labelling, neutralization); plus, the seeded default terminal since v0.2.66, **EUROGATE Container Terminal Hamburg**: berthing charge (1.04 EUR/GT first 24 h of lay time, 0.60 per commenced 12 h thereafter; Prices and Conditions 2.1.1–2.1.2), container handling (358.00 per move, 5.1.1 — a published rate), security charge (24.95 per container, 13.1), the social fund surcharge (1.5% on berthing + handling excluding security, 1.3.13), and the optional ordered services (lashing 47.00, twistlocks 24.00, IMO 87.00, small-call minimum 3,308.00 at ≤20 handled containers, lay-by 1.34/TEU per commenced 24 h, reefer 181.50 first / 144.50 subsequent 24 h); and **City of Hamburg (BUKEA)** — the MARPOL I/IV/V ship waste fee with its GT cap and the application-based reductions (short-sea, alternative fuel, sustainable waste), off by default.

**Lay-time input.** The Hamburg port-specific card exposes a lay-time input (Lay Time at Berth, hours; defaultCall seeds 16 h) feeding the terminal layer's lay-time basis — the Eurogate berthing charge at the default operator (v0.2.66) and the HHLA tonnage dues at the entered variant — and, via the demurrage's `fallback_hours`, the HPA demurrage when no separate Total Time in Port is entered. Its helper text carries the tariff caveats: lay time runs berthing to casting off; Sundays and holidays count only if worked (modeled as a simple hours input per the extraction note; sources: Eurogate Prices and Conditions 2.1.1–2.1.2, HHLA Quay Tariff S4 clause 1.2). Blank = not entered: the terminal lay-time charge and demurrage are absent from the result (zero-collapse), never seeded.
**Estimated parameters.** Since v0.2.66 the Hamburg handling line is a published rate at the default operator (Eurogate 5.1.1, 358.00 per move) and carries no estimate flag; the HHLA variant's handling estimate (the same 358 EUR default, contract-anchored) remains estimate-flagged on variant calls. Towage (default 15,000 EUR per call, no published tariff) remains an estimated parameter under both operators; the engine emits an `estimated_parameter` quality flag on these lines regardless of user override The engine Tier resolves per the classification rule (v0.2.29, amended v0.2.44): explicit entry wins; otherwise a present build year infers the tier per MARPOL Annex VI Regulation 13 construction dates (2016+ → Tier III, 2011–2015 → Tier II, 2000–2010 → Tier I, pre-2000 → Tier 0), flagged as an assumed parameter; a blank build year keeps the worst-case Tier 0 default with its existing flag.

**Towage fee family.** Towage is added to the shared fee-family taxonomy (segment: vessel call). Where a port does not levy towage, the comparison view shows "not charged" for the family rather than hiding the row. Towage is deliberately not mapped to connection_fee or any other family. As of v0.2.33 every port in the 2026 set carries an estimated towage rule (Gothenburg and Helsingborg per tug-assist with LOA-class tug defaults, Hamburg a per-call estimate) — all estimate-flagged into the estimated-parameters subtotal, never verified data.

### 5.4 Helsingborg 2026 Port File (v1)

The Helsingborg port file (`core/data/helsingborg_2026.yaml`, port id `helsingborg`, currency SEK, effective 2026) is a self-contained silo encoded under the same schema, with three billers: **Port of Helsingborg** (Helsingborgs Hamn AB acts as both port authority and terminal operator of the West Harbour container terminal — a single biller for port dues, the waste/environmental fee, port security, cargo dues, stevedoring, storage, and ancillaries) and **Sjöfartsverket** (the national vessel fee 10 NT classes × environmental classes A–E, readiness fee, pilotage start + per-commenced-half-hour + ordering fee — the national tables transcribed in full into this file, never referenced from another port file; the engine and the fee-family vocabulary are the only shared assets). Towage is provided by commercial operators with no published tariff and is encoded as an estimated parameter.

**Port-specific rules.** Flat port dues 6.85 SEK/GT (all vessel types, no banding); the waste/environmental fee as the highest of 0.75 SEK/GT versus 25,000 SEK per call (break-even 33,333 GT; the selection rule is an assumption recorded in the extraction reference); cargo due 625, port security 78 (doubled for vessels without a valid ISSC), and LO-LO stevedoring 890 SEK per unit; the Emergency Energy Surcharge encoded as a datestamped parameter with the HVO band table (September 2026 level: 35 SEK/move), never a constant; environmental discounts of 10 % (ESI ≥ 30 or Clean Shipping Index class 4) plus a further 10 % for ≥ 30 % fossil-free fuel, stacking additively to 20 %; long-stay surcharges after four days (100 SEK per commenced metre LOA per 7-day period on port dues, 4.00 on waste); storage with seven free days for full units plus the empty-unit rates. The port's Clean Shipping Index discount (class 4 on a 1–5 index scale) and Sjöfartsverket's environmental class (A–E) are two different scales and must never be conflated: they are distinct call inputs.

**Estimated parameters.** Towage is a quality-flagged, user-overridable estimate (default 60,000 SEK per tug-assist) with tug-count defaults by LOA class encoded as data (< 150 m: 0; 150–250 m: 1; > 250 m: 2 — spec 3.3: defaults are suggestions, the user may always override). Pilotage default hours follow the same LOA classes (2/3/4 h) as declared suggestion values.

**Not yet encoded.** Dalshult stuffing/stripping (third party, no published rates) and OOG handling ("as per request") are surfaced as not-yet-encoded notices rather than estimates. Godsavgift was encoded at v0.2.61 (§4.2.5): the cargo-tonnage derivation now fires it from the call's container counts and the shared planning weights.

**Sjöfartsverket frequency discount.** The percentage of the vessel + readiness fees payable by calls at the port per calendar month (1–2 calls 100 %, 3 calls 75 %, 4 calls 50 %, 5 calls 25 %, 6 or more 0 %) is encoded as a per-biller `frequency_discount` block keyed on the listed fee families, itemized as its own negative line on the biller — never folded silently into the base fees.

**Per-biller surcharges (Hafenfonds).** The Hamburg Hafenfonds (port fund) levy of 1.5 % on HHLA quay-tariff fees (excluding storage and the estimated handling parameter) is encoded as a surcharge rule on the HHLA biller object in the port file, not a hardcoded line item, so a future terminal biller (e.g. Eurogate) can carry its analogous social-fund rule as data.

**Handling-hygiene rule (v0.2.24).** The Hamburg model is a deliberate hybrid: an HHLA terminal call (tonnage dues, gangway, supervision, security, storage — all from the HHLA quay tariff) with a single handling line whose default is anchored to Eurogate's published waterside lift charge (358.00 EUR per move, Eurogate 5.1.1) because HHLA's own rate is unpublished (S4 2.1.2: upon request, individually negotiated). This hybrid must never be presented as an Eurogate terminal call: the handling line is labeled "Container Handling (est., Eurogate anchor)" in every rendering (per-port view, comparison view, biller breakdown), so the estimate status and its source are visible without expanding any detail. A Eurogate terminal variant is deferred until Eurogate's full quay tariff (their non-lift charges) is extracted; if that extraction later happens, terminal selection (spec 3.2) becomes the mechanism for separating the two operators, with no mixing of one operator's dues with the other's lifts. A terminal-hygiene constraint locks the structure against future edits: exactly one terminal_handling rule exists in the Hamburg file, it carries the estimated_parameter block, and its biller is HHLA.

**Estimated-parameter separation.** The output contract carries, per port computation: the grand total, an estimated-parameters subtotal (the sum of all fee lines carrying an estimated-parameter flag), and the total without estimates. The comparison view and the per-port total strip render all three symmetrically for every port (Hamburg: handling and towage; Helsingborg: towage; Gothenburg: none), so a port-fee-level comparison is never dominated by an estimate — Hamburg handling is roughly seventy percent of its total and would otherwise dominate the tri-port comparison. The mechanism is generic and port-agnostic: driven entirely by the flags each port file's rules emit, never by port-specific UI logic.

## 6. Currency Handling

- All arithmetic is performed in the tariff's native currency (SEK, EUR, DKK, PLN). Per-port result views render native currency exclusively; no converted figure appears in any per-port view.
- **Cross-currency comparison (v0.2.31).** The comparison view compares ports that bill in different currencies. No cross-currency comparison may ever be performed on raw amounts: a EUR total is never numerically compared against a SEK total. Every cross-port aggregate row (grand totals, segment totals, fee-family rows, the vessel-access aggregate and its effective per-GT) renders each port's native-currency figure as primary and a converted figure as secondary ("802,180 EUR ≈ 9,042,000 kr"). Converted figures are derived, labeled as such per the derived-metric contract (v0.2.30), and never appear without their rate and date.
- **Ranking integrity (v0.2.31; basis resolution amended v0.2.59).** Wherever the comparison view orders or ranks ports (cheapest / most expensive, and the column/card ordering itself), the ordering uses the converted comparison basis; the display keeps native-primary. The comparison basis is SEK by default. Since v0.2.59 the basis and each port's conversion path resolve from data, not hardcoded currency pairs: the comparison builds a ComparisonBasisContext from the registry's exchange-rate rows toward the declared basis, and a port whose currency has no declared conversion path fails loudly at conversion and ranking — a future DKK port is impossible to add without declaring its rate, and no ranking ever compares raw amounts across currencies.
- **Rate input (v0.2.31).** The exchange rate is a user-editable kr-per-EUR input with a documented default stored in the data (core/data/exchange_rates.yaml, emitted to the registry at conversion; recorded source: the ECB euro reference rate, verified at implementation time with its value and as-of date). No runtime API calls — the rate is static, versioned data, like the tariff data. Blank or invalid rate input falls back to the documented default with a visible fallback flag, never to an unconverted comparison. A single-currency view may be revisited later only as an output-side rendering under this same rate-and-date contract, never as a replacement of native figures. (Amended v0.2.59: a currency beyond the currently rendered pairs is added by declaring its rate row in exchange_rates.yaml — the conversion path is data, one row per currency toward the basis; the v0.2.39 rate-input disclosure collapse and the v0.2.58 naming conventions hold for every rendered currency pair.)
- **Removed control (v0.2.31).** The v0.2.20 "express totals in one currency" optional final step (ECB feed fetch, display-currency select, manual-rate override, converted-totals table) is removed: it was non-functional (the fetched-rate path did not convert the comparison's own figures), and its label described the wrong contract (blanket conversion replacing native figures). The cross-currency contract above replaces it.
- The user's chosen exchange rate is never part of any calculation input; it converts figures for comparison display only.

## 7. Data Workflow and Repository Layout

Tariff PDFs are stored in the repository as the source of truth but are never parsed at runtime. Fee rules are extracted from PDFs (in this Vibe project) and encoded into structured port files, referenced by filename and page.

```text
/ports
  /segot (Gothenburg)     port.yaml, /billers (authority.yaml, terminals...), /docs (tariff PDFs)
  /deham (Hamburg)        — multiple terminal operator billers
  /sehbg (Helsingborg)    — single biller (authority-owned terminal)
  /segvle (Gävle)
  /plgdn (Gdansk)
  /debrv (Bremerhaven)
  /dkaar (Aarhus)
/vessels  vessels.yaml (curated named-vessel table)
```

Structured human-readable files are preferred over a database for version 1: YAML for authoring (human-editable tariff maintenance), JSON as the interchange format the application consumes. All files are reviewable on GitHub, fully versioned, and convertible to a database later without redesign. Prior-year tariff versions are retained in each port directory, distinguished by effective-from dates.

**Worked-example cross-check reference (v0.2.36).** `docs/TARIFF_EXAMPLE_VERIFICATION.md` is the standing record of every tariff-sheet worked example in the 2026 source set, its reconstruction on the engine, and the reconciliation verdict (match, tool defect, assumption difference, cancelling-error coincidence). It governs tariff-year updates: when a new tariff year is extracted, the document's entries are re-run against the new year's published examples before the new port files are accepted, and its inventory is extended with any examples the publishers add. Its findings are diagnoses, not fixes: each defect it records is repaired and re-pinned in its own pass, never silently inside an extraction or health check.

**Pin-source hierarchy (v0.2.37).** A test pin's expected figure is sourced by
precedence: (1) the published worked example (tariff sheet, lathund row,
regulation worked table) — the pin cites its example (document, page/row);
(2) the extraction reference's own figure, where no publisher example exists
(builder-constructed checkpoints); (3) a derived default, explicitly labeled
as derived and never presented as published. Where a pin conflicts with a
published example, the pin is wrong, not the example.

**Excess-units reductions (v0.2.37).** Some tariff clauses discount only
the portion of a per-unit fee beyond a threshold (SJÖFS 2025:5 §25: 40% off
the lotsningsavgift for the piloted time exceeding 7 hours — i.e. only the
half-hours beyond the first 14, start fee unreduced). The adjustment
language expresses this as `apply_to: excess_units` with
`threshold_units: N`: the first N units bill at the full rate, each unit
beyond them at the adjusted rate, and the adjustment never touches any
other line (a start fee carries no such adjustment). Whole-line percentage
adjustments remain the default for every other clause.

**Terminal no-charge bands (v0.2.37).** A lead-time band set may end in a
no-charge region: SJÖFS 2025:5 §11 charges the ordering fee only when the
pilot is ordered less than 5 hours ahead, so the published 4h–4h59 band is
the last charging band (`4_5h`) and a lead ≥ 5 h matches no rule and
charges nothing. Band sets must encode their true upper bound; an
open-ended top band that silently bills past the published range is the
defect class this rule eliminates.

## 8. Application and Deployment

- Web form input (vessel and call parameters) → itemized per-port cost table, totals, ranking, CSV/JSON export.
- REST API returning the same results as JSON (web UI built on it).
- Deployable to any static host as a stateless single service (aside from an exchange-rate cache and tariff data files). The deployment target is an implementation choice, changeable without spec changes; the spec's requirement is that a deployment be verifiable at the served artifact (fresh deployment record and served bundle markers), never by pipeline exit status alone.
- **Delivery protocol (v0.2.34, amended v0.2.38).** Default delivery of a work pass is a single direct push to main per pass: the full local suites are run and green, the spec version and changelog row are bumped in the same commit (the version guard fails the push otherwise), the change is pushed, and the post-deploy section 8 verification (deployment record with served-bundle markers) is reported. Draft pull requests are reserved for passes the user explicitly designates contentious (figure-moving changes); where one exists, its URL is reported on creation and it is marked ready for review on the user's approval. Merging is a human-only step: builder sessions cannot merge pull requests from this environment, a builder must never interpret main advancing as its own merge succeeding, and a builder never performs or retries merges. The previous reports claiming a builder merged PR #3 and PR #4 were mistaken — the user merged them from the UI. This amendment supersedes the v0.2.34 draft-PR default.
- **Deployment-verification protocol (v0.2.32).** The first fetch of a freshly deployed bundle has repeatedly returned a truncated body (observed pattern: 9,379 bytes of a much larger document) — a CDN/edge propagation artifact, not a build defect. Verification therefore always: (1) fetches the served artifact with a cache-bypassing request (nocache query parameter or equivalent) on the first failure; (2) confirms the full expected byte length of the body before checking any content markers; (3) retries on a short interval until the full body is served, and only then asserts the served-bundle markers (version strings, section headers, theme-toggle label). A marker check against a truncated body is a false negative and is never reported as a deployment failure without the retry-and-length protocol first. The pass-type markers ride along when the pass introduces a new rendering path (v0.2.39: a mobile-path marker; v0.2.42: a derivation-path marker).
- **Served-bundle identity when the JS asset is unfetchable (v0.2.55, standing method).** The deployment-verification protocol's served-bundle marker step assumed the JS asset itself can be fetched. On this deployment target the served JS bundle is repeatedly unfetchable by sandboxed verification tooling (observed across the v0.2.53 and v0.2.54 deliveries: the HTML shell fetches, the JS asset is refused for automated reading). The accepted identity proof in that case, used as the standing method rather than a per-pass deviation: (1) the deploy workflow's build log lists the artifact it uploaded (`File sizes after gzip` and the upload-artifact step's file listing); (2) the production build emits a content-hashed bundle filename (`static/js/main.<hash>.js`, the Create React App deterministic content hash — identical content implies identical filename); (3) the local zero-warning build emits the same filename; a filename match between the deploy log's artifact listing and the local build is therefore a content-identity proof of the served bundle; (4) the served HTML shell is fetched with cache bypass to confirm the deployment serves the application. Together the deploy-log artifact listing, the filename match, and the live HTML shell establish the served-artifact identity; the pipeline exit status alone remains insufficient, as ever.

- **Authoritative spec check (v0.2.35).** The authoritative verification of the delivered specification is the raw.githubusercontent copy at the delivered commit SHA (`https://raw.githubusercontent.com/Rekkike/VibesandTariffs/<commit-sha>/docs/SPECIFICATION.md`). The jsdelivr CDN mirror of the same file is eventually-consistent: a stale copy observed shortly after a delivery is a propagation artifact of the mirror, never evidence of a deployment defect, and is never reported as staleness of the repository or the served bundle.
- **Version guard on the merge path (v0.2.35).** A CI check (`.github/workflows/spec-guard.yml` running `core/scripts/check_spec_version.js`) fails any pull request or push to main whose changes affect engine, data, or web behavior (paths `core/src/`, `core/data/`, `core/scripts/`, `web/src/`) unless the same change adds a new specification changelog version row. The guard's own CI includes a demonstration job: a deliberately un-bumped fixture must fail the check (exit 1) for the guard itself to pass, so the guard can never silently stop guarding.

Evidence reviewed: the IMO 1969 International Tonnage Convention sets only a floor (NT ≥ 0.30×GT), no fixed ratio; observed container vessels range ~45–58% (Ever Given 220,940 GT / 99,155 NT ≈ 45%; Clementine Maersk 91,921 GT / 53,625 NT ≈ 58%; Vistula Maersk 34,882 GT / 16,947 NT ≈ 49%), and bulk carriers run 52–63%. ### Audit Record — v0.2.23 (Hamburg, Helsingborg, tri-port sanity check)

The six audit checks (rule inventory, firing, checkpoint coverage, discount/condition semantics, estimate integrity, silo integrity) were applied to the Hamburg and Helsingborg port files, followed by a tri-port verification running the four library vessels through all three ports with identical call parameters. Findings and resolutions:

- **Hamburg rule-inventory gaps (fixed):** the HHLA 45-ft storage rates (92.20 EUR/day, import doubling/tripling and export doubling as for the other sizes) and the gassing-space container services (176.90 EUR 20-ft, 240.70 EUR 40-ft) from reference §5.2/§5.3 were absent from the port file; both are now encoded with full source references and optional call inputs, default off.
- **Hamburg verified correct:** CP1 reproduces the HPA worked example to the cent (32,838.88 / 7,022.54 / 39,861.43); CP2–CP5 match all reference figures; the HPA minimum fee (43.56), demurrage minimum (44.38), and berth-fee minimum (16.84) apply with visible "min applied" labels; the Hafenfonds surcharge excludes storage and terminal handling as the reference requires; the GDWS dues cap (5,322) and pilot-fee cap (4,100) hold; SG 2/SG 3 and the penalty items remain modelled as notes, not charges, per reference §3.4.
- **Helsingborg verified correct:** CP1–CP5 reproduce all reference figures; all §3.9 ancillaries encode and fire; §9 not-modelled items (godsavgift, Dalshult, OOG, scrubber waste, pumping) are surfaced as notices and never estimated; the CSI-1–5 port discount scale and the Sjöfartsverket A–E environmental class are kept strictly separate.
- **Gothenburg firing defect (fixed):** the APM idle-berth service (500 SEK/h, explicit request only) fired silently whenever pilotage hours were set. It is now gated behind a dedicated idle-berth-hours input; blank input means the service was not ordered.
- **Contract-vs-published caveat (implemented):** defined at v0.2.4 but not previously carried in the data model. A rule-level caveat field now flows onto every result line as a quality flag; the APMT Gothenburg handling charges (377/535 SEK) carry it.
- **Sjöfartsverket environmental class default (corrected):** the form defaulted to class A (most favourable); the documented default (Helsingborg reference §10.2) is E (not registered), matching the engine's least-favourable fallback. The UI default is now E, a documented choice — the A-vs-E difference swings the vessel fee by roughly 64,600 SEK for a mid-size vessel and must never be an accident.
- **Gothenburg ancillary inputs (added):** fresh water (m³ above 50), sludge excess (m³ above 11), scrubber waste (checkbox), and break bulk (1,000-kg units) now have form inputs, gated so blank values never fire the rules.
- **Tri-port sanity check:** with identical call parameters (first call of month, discharged-only container counts split by size bucket, pilotage hours per LOA class, ordering lead ≥ 4 h, zero storage, valid ISSC, gangway class per vessel), Hamburg and Helsingborg reproduce their reference checkpoints exactly for all four vessels; Gothenburg was computed fresh and decomposed line by line. The known magnitude spread (Gothenburg's published handling roughly a third of Helsingborg's per-unit all-in; Hamburg's handling estimate roughly 4,000 SEK/move) is expected — the check confirms each port's decomposition is line-by-line correct, not that the ports equalize.

### Resolved Decisions (for reference)

- File format: YAML for authoring, JSON as interchange. (Was open item 1.)
- Adjustment stacking: per-tariff declaration; multiplicative as fallback where a tariff is silent. (Was open item 3.)
- Missing-parameter fallback: assume least favourable value with visible notice.
- Multi-terminal default: present alternatives side by side; user must select; no arbitrary default.
- Data validation: unknown fee family prompts user with quality warning; banded gaps/overlaps rejected at load.
- Tug input: port/LOA-class defaults as suggestions; user may always override.
- Tariff versioning: prior versions kept loaded; engine handles structural form changes across years.
